### Quality gap being closed

The OPT-016 Rank 1 kernel is MMA in name but not llama.cpp MMQ quality:

1. Outer K-step is 32, so each Q4_K/Q6_K 256-value superblock is decoded eight times with scalar 32-lane loops.
2. Activations are fused BF16→Q8_1 warp-max inside the compute kernel rather than `quantize_mmq_q8_1` into `block_q8_1_mmq`.
3. SRAM has no `MMQ_TILE` bank-conflict padding (`K % 8 == 4`) and no DS4/D4 Y scale layout.
4. Block is 1D 256 threads; llama.cpp Ampere uses `dim3(32, 8)` so `threadIdx.y` is the warp index.

### Q4_K/Q6_K quality kernel (do not vendor `mmq.cuh`)

Implement a **separate** Q4_K/Q6_K quality kernel in `cuda/quant_mmq_mma.cuh` (included from `cuda/quant_mmv.cu`; **do not add a Makefile object** and **do not edit `NVCCFLAGS`**). Do not retarget the existing `quant_mmq_mma_kernel` Q8_0 specialization; leave the OPT-017 Q8_0 path behaviorally intact (1D 256 threads, K-step 32, fused SRAM staging, no `q8_workspace`).

Q4_K/Q6_K quality geometry (llama.cpp Ampere table intersected with sm_120):

- Block: `dim3(32, 8)` (256 threads, `MMQ_NWARPS=8`). Grid: `(ceil(output_rows/128), ceil(prompt_rows/J))`.
- I = 128 output rows per block. J in `{32, 64, 128}`.
- `MMQ_ITER_K = 256` (one Q4_K/Q6_K superblock). `columns % 256 == 0` remains required.
- Require the existing prompt Q8 workspace (`q8_prompt_workspace_bytes`); reject `nullptr` with `cudaErrorInvalidValue`.

**Y quantize (primary, llama.cpp `quantize_mmq_q8_1` analog):** a dedicated kernel reads token-major BF16 `[prompt_rows, columns]`, writes `block_q8_1_mmq` tiles into `q8_workspace` (same byte count as today's `Q8Block` packing). Layout:

- 128 int8 values + 16-byte scale/sum padding per 128-value group (`sizeof == 144`).
- Q4_K uses DS4 (`half2` scale + partial sum per 32 values).
- Q6_K uses D4 (one float scale per 32 values).
- Scale rule stays warp-max / 127 (same as today's MMA staging and `quantize_bf16_q8`). Do not change CUD-002 numbers to chase a different quantizer.

`launch_quant_mmq_mma` / `_tile` run quantize then MMA on the same stream. No extra persistent `cudaMalloc`. Production `launch_quant_mmq` already has `q8_workspace` and must pass it through.

**X load (llama.cpp `ggml_cuda_mmq_load_tiles_q4_K` / `q6_K` Turing MMA path):**

- Q4_K: `get_int_b4` (or 32-bit aligned load) from the 144-byte GGUF block; store `(qs >> 0) & 0x0F0F0F0F` and `(qs >> 4) & 0x0F0F0F0F` into padded SRAM; unpack 6-bit scales/mins into `half2` `(d*sc, -dmin*m)` at MMA stride. Do not scalar-decode 32 lanes per K=32.
- Q6_K: packed low-nibble / high-2bit load into MMA SRAM plus per-group int8 scales, matching `ggml_cuda_mmq_load_tiles_q6_K` MMA path.

**Dot (llama.cpp vec_dot MMA):**

- Q4_K: after nibble unpack, `mma.sync.aligned.m16n8k32.row.col.s32.s8.s8.s32` then `acc += dmA.x * dsB.x * float(C) + dmA.y * dsB.y` (`ggml_cuda_mmq_vec_dot_q8_1_q8_1_mma`).
- Q6_K: `ggml_cuda_mmq_vec_dot_q6_K_q8_1_mma` analog (k16 fragments + scale bytes × `dA` × `dB`).
- Y tiles copy as contiguous ints from global `block_q8_1_mmq` into shared `MMQ_TILE_Y_K` (40 32-bit slots per J row: 32 qs + 4 scale/sum + padding). Two Y halves per 256-K X tile, matching `mul_mat_q_process_tile`.

**No-check vs checked:** production FFN and attention-output shapes at 2048 and 4096 have `output_rows % 128 == 0` and `prompt_rows % J == 0` for J=128. Dispatch a bounds-free kernel in that case. Component odd sizes (`8, 9, 64, 65` rows; `17×256`) keep the checked kernel. Partial tiles never expose padding as a result.

### Q6_K CUD-002 stop (locked 2026-09-08T16:39:59Z diagnostic)

Independent diagnosis: required Q6_K `64×5120×6144` misses unloosened CUD-002 versus `launch_quant_mmq_variant` because **INT8 MMA grouped dots are a different FP32 association** than the scalar variant's per-element `__fmul_rn`/`__fadd_rn` + warp shuffle, not because packed-tile / Y-layout indexing is still wrong.

Evidence:

- Live quality kernel: `max_abs=0.000946044922` `rms=0.000258449378` (limits `5e-4` / `2.5e-4`). Q6_K K=256 cases (`8×17×256`, `9×64×256`, `17×128×256`) pass. Q4_K including `8×1024×5120` passes (`max_abs=0.000366210938` `rms=0.000154442241`) with double accumulators.
- Rank-1 K-step-32 Q6 MMA (integer `m16n8k16` then float `dB*(sc0*C0+sc1*C1)`, including double acc) misses the same shape class. Full-superblock K=256 already exercises both Q6 halves; a remaining half-1 scale/qh bug would have failed those small cases.
- Quality Q6 load-tiles / SRAM stride 76 / `x_df[i*sram_stride]` / `x_sc[i*sram_stride + lane%4]` / k16 `ldmatrix` + `load_b_generic_k16` match llama.cpp `cc83d7b` Turing MMA `ggml_cuda_mmq_load_tiles_q6_K` and `ggml_cuda_mmq_vec_dot_q6_K_q8_1_mma`. Y D4 (`4` float scales + `128` qs, `MMQ_TILE_Y_K=36`) matches `block_q8_1_mmq` / `MMQ_Q8_1_DS_LAYOUT_D4`. `64%128 != 0` selects the checked kernel, but `5120%128==0` so X loads are identical to the no-check path; Y padding is not written.
- llama.cpp Turing Q6 epilogue uses **float** `tmp += (C0*sc0+C1*sc1)*dB` over `k01`, then `sum += tmp*dA` once per 128-K Y-half. Quartz uses **double** `sum += packed*dB*dA` inside `k01`. That is a real association delta versus llama.cpp, but it is not the CUD-002 miss: the admitting reference is the Quartz variant, which does one float FMA per K-element then a 32-lane shuffle tree.
- Host association model (synthetic Q6 block entropy + BF16→Q8 max/127, one output element): K=256 abs≈3.6e-6; K=6144 abs≈6.1e-4 already over `5e-4`. llama.cpp float-tmp and float-acc variants still ≈5.8e-4–6.0e-4.
