# OPT-012 — Add stable-address prompt CUDA graphs

## Control

- Primary ID: `OPT-012`
- Coupled IDs: `none`
- Dependencies: `OPT-003`, `OPT-011`; both done at planning admission
- Status: `done`
- Ledger acceptance: Common 4,096-token prompt paths replay from stable addresses with graph/non-graph equality and reconciled memory

## Goal and boundaries

Capture, instantiate, upload, and replay **64 stable-address prompt FFN
subgraphs** at the production 4,096-row geometry, bound to the same
`ResidentModel` and `SchedulerWorkspace` as the existing 64 decode FFN graphs.
A full 4,096-token fused prompt chunk must `cudaGraphLaunch` those executables
from the captured prompt-scratch and weight pointers, remain byte-exact versus
the retained ordinary fused launches, and appear as measured graph owners in
the post-graph 128K memory ledger with the 1.5 GiB reserve still intact.

- Constraints: keep C++17, CUDA 13.0.2, `sm_120`, `--fmad=false`, 256 threads,
  BF16 activation/KV storage, FP32 residual and GDN recurrence, OPT-008
  `kPromptChunkRows = 4096` and `prompt_chunk_rows_ = min(4096, capacity)`,
  OPT-011 fused overlapped production plus retained unfused serial path,
  OPT-009 MMQ dispatch, OPT-010 physical KV scatter, SES-002
  candidate-versus-committed isolation, and all frozen
  SCH-002/OPT-003/OPT-008/OPT-011 numeric and exact-state gates. Prompt graphs
  are additional CUDA graph objects, not extra `cudaMalloc` scratch; workspace
  byte formula `160,380,416 + 96*C + 404,992*R` stays unchanged. Do not edit
  `Makefile`; build the new diagnostic with the same explicit pinned `nvcc`
  command pattern as OPT-011. Exclusive RTX 5090 work stays serialized. Do not
  capture embedding token rows, GDN state-owner swap, attention position or
  causal extent, KV destination, host output copies, or atomic commit. Do not
  add CUDA graph parameter updates.
- Non-goals: associative/block-parallel GDN scan (`OPT-013`); changing MMQ
  tiles (`OPT-009`); changing committed KV layout (`OPT-010`); changing the
  4,096-row outer chunk or 64-row internal GDN scan (`OPT-008`/`GDN-002`);
  whole-chunk or whole-token graphs; capturing mixer GDN/attention; graphing
  the unfused serial path; requiring a graph-versus-ordinary speedup gate;
  claiming end-to-end prefill/decode speedup, comparative 5% gates, or 128K
  quality recovery; reopening MEM-001/MEM-002/EDU-039/QLT-001 as coupled work;
  editing `plan.md`.
- Plan impact: `none`
- Affected interfaces: no public Engine, CLI, server, model, or JSON API
  changes. CUDA-internal `SchedulerGraphs` gains a second 64-graph prompt FFN
  set captured only when `workspace->prompt_chunk_rows_ == 4096`.
  `execute_prompt_chunk` and `sync_tokens` gain an optional trailing
  `SchedulerGraphs*` defaulting to `nullptr`. Production `Session::sync` passes
  the session graphs so 4,096-row chunks replay prompt FFN graphs and one-row
  tails replay the existing decode FFN graphs. New schema-1 contract and
  fixture files are task evidence, not a public protocol. The MEM-001/MEM-002
  post-graph fixture is remeasured as OPT-012 evidence without reopening those
  done tasks.
- Implementation classification: not mechanical. This changes CUDA graph
  ownership, capture/replay lifetime, prompt/decode launch selection, and the
  128K graph-memory owner set. Use the CUDA/numeric implementation agent, not
  a mechanical path.
- Documentation stage: required. Update the existing stable-address graph,
  post-graph memory, and full-prefill handbook chapters plus `docs/sources.md`
  and one non-final then final OPT-012 audit row. Do not add an EDU task;
  EDU-039 already covers the graph chapter.

## Implementation decisions

Keep decode `execute_ffn` graphs, `execute_token` replay, OPT-011 fused and
unfused prompt orchestration, MMQ kernels, GDN scan windows, attention prepare
kernels, `kPromptChunkRows`, workspace byte formula, checkpoint pack/unpack,
and public APIs unchanged. Add a second captured FFN set for the production
4,096-row prompt path and wire it through `sync_tokens`.

### Prompt FFN helper (capture and ordinary launches)

Add `execute_prompt_ffn` in the anonymous namespace of
`cuda/full_scheduler.cu` beside `execute_ffn`. It is CUDA-internal, not a
header API. Signature:

```text
cudaError_t execute_prompt_ffn(
    const DeviceCommonLayer& layer,
    const float* residual,
    SchedulerWorkspace* workspace,
    float* after_mixer,
    float* output,
    const float* next_input_norm,
    std::size_t token_count,
    cudaStream_t stream) noexcept
```

Body, in this order, using existing launchers:

1. `launch_residual_add_norm_rows_fp32_to_bf16(residual,
   workspace->prompt_mixer_output_, layer.ffn_norm, kResidualWidth,
   token_count, after_mixer, workspace->prompt_normalized_, stream)`
2. `matrix_prompt(layer.ffn_gate, prompt_normalized_, token_count, workspace,
   prompt_projection_a_, stream)`
3. `matrix_prompt(layer.ffn_up, prompt_normalized_, token_count, workspace,
   prompt_projection_b_, stream)`
4. `launch_swiglu_bf16(prompt_projection_a_, prompt_projection_b_,
   token_count * internal::kFfnWidth, prompt_projected_bf16_, stream)` using
   the same element count the fused prompt path already passes (`cuda/full_scheduler.cu:2020`)
5. `matrix_prompt(layer.ffn_down, prompt_projected_bf16_, token_count,
   workspace, prompt_mixer_output_, stream)`
6. If `next_input_norm != nullptr`: fused
   `launch_residual_add_norm_rows_fp32_to_bf16(after_mixer,
   prompt_mixer_output_, next_input_norm, ..., output, prompt_normalized_,
   stream)`. Else: `launch_residual_add_fp32(after_mixer, prompt_mixer_output_,
   token_count * kResidualWidth, output, stream)`

This is the current fused prompt FFN sequence, including mixer
residual-plus-FFN-norm, because those pointers (`prompt_mixer_output_`,
`ffn_norm`, prompt residuals, `prompt_normalized_`) are workspace- or
weight-stable. Mixer GDN/attention launches stay outside the graph and must
finish writing `prompt_mixer_output_` before replay, matching decode writing
`mixer_output_` before FFN graph launch.

Production fused `execute_prompt_chunk` must call this helper instead of
open-coding those launches, so capture and ordinary fused FFN are the same
function. Unfused serial FFN stays open-coded and is never captured.

### SchedulerGraphs ownership

Keep the existing 64 decode `graphs_` / `executions_` arrays. Add:

```text
std::array<cudaGraph_t, internal::kModelLayerCount> prompt_graphs_{};
std::array<cudaGraphExec_t, internal::kModelLayerCount> prompt_executions_{};
std::size_t decode_graph_count_ = 0;
std::size_t prompt_graph_count_ = 0;
std::size_t prompt_rows_ = 0;
```

Replace the single `graph_count_` field. Public accessors:

- `graph_count()` returns `decode_graph_count_ + prompt_graph_count_`
- `decode_graph_count()` returns 64 after a successful create that captured
  decode FFNs
- `prompt_graph_count()` returns 64 when prompt graphs exist, else 0
- `prompt_graph_rows()` returns `kPromptChunkRows` when prompt graphs exist,
  else 0
- `allocated_bytes()` remains the single CUDA free-memory delta covering the
  whole `create` (decode then prompt)

`matches(model, workspace)` stays the decode binding check:
`decode_graph_count_ == 64 && model_ == &model && workspace_ == workspace`.
`execute_token` is unchanged except it continues to use `matches`.

`release` / move destroy and transfer both graph sets, including
`prompt_rows_`. Partial failure of either loop still `release()`s everything
and returns an explicit CUDA status. No half-created set is replayable.

`create` sequence:

1. Reject the same invalid inputs as today.
2. `cudaMemGetInfo` into `free_before`.
3. Create one non-blocking capture stream.
4. Existing 64-layer decode capture of `execute_ffn(..., PointwisePath::kFused,
   stream)`, instantiate, upload; increment `decode_graph_count_` per success.
5. If `workspace->prompt_chunk_rows_ == kPromptChunkRows` (4096): for each
   layer, `cudaStreamBeginCapture` / `execute_prompt_ffn` with
   `token_count = 4096`, `residual = prompt_residual_a_`,
   `after_mixer = prompt_residual_b_`, `output = prompt_residual_a_`,
   `next_input_norm` from layer+1 or `nullptr` on layer 63; end capture into
   `prompt_graphs_[layer]`; instantiate `prompt_executions_[layer]`; upload;
   increment `prompt_graph_count_`. Set `prompt_rows_ = 4096` only after all
   64 prompt uploads succeed.
6. If `prompt_chunk_rows_ != 4096`, skip prompt capture; `prompt_graph_count_`
   and `prompt_rows_` stay 0. Capacity-33 decode diagnostics and capacity-3/65
   scheduler tests therefore still own 64 decode graphs only.
7. Synchronize the capture stream, `cudaMemGetInfo` into `free_after`, destroy
   the stream, store `allocated_bytes_ = free_before - free_after` (zero if
   inverted). Bind `model_` / `workspace_`.

Capture mode remains `cudaStreamCaptureModeThreadLocal`. Prompt FFN kernels
are launched on the capture stream; replay later uses
`workspace->prompt_compute_stream_`. Instantiated graphs may launch on a
different stream than the capture stream.

Do not capture embedding, mixer GDN/attention, logits, D2H, or scatter.
Token-ID overlays, frontier, and committed KV destinations change per chunk
and would replay stale scalar arguments.

### execute_prompt_chunk replay

Extend `execute_prompt_chunk` with one optional trailing argument:

```text
SchedulerGraphs* graphs = nullptr
```

Default remains ordinary fused production for existing diagnostics. Update
every friend declaration to the new signature.

Validation additions:

- `graphs != nullptr && path != kFusedOverlapped` → `kInvalidArgument` before
  any publication (same rule as decode graphs requiring fused pointwise).
- `graphs != nullptr && !graphs->matches(model, workspace)` →
  `kInvalidArgument` before any publication.

Replay predicate, evaluated each layer after mixer writes
`prompt_mixer_output_`:

```text
const bool replay_prompt_ffn =
    graphs != nullptr &&
    graphs->prompt_graph_count() == internal::kModelLayerCount &&
    token_count == graphs->prompt_graph_rows();
```

When `replay_prompt_ffn` is true, `cudaGraphLaunch(prompt_executions_[layer],
stream)` on `prompt_compute_stream_`, bump a new
`PromptPipelineCounters::prompt_graph_launches` field, and do not bump
fused-residual-norm or residual-add counters for FFN-internal kernels (those
launches live inside the graph). When false, call `execute_prompt_ffn` on the
fused path or keep today's open-coded unfused FFN.

Tails with `2 <= token_count < 4096` on a 4096-bound graph object therefore
use ordinary fused `execute_prompt_ffn`. One-row remainders never enter
`execute_prompt_chunk`. Small workspaces never create prompt graphs, so fused
prompt chunks there also use ordinary launches.

Layer-0 input RMSNorm, mixer MMQ/GDN/attention, last-row logits, async D2H,
all-layer scatter, stream joins, cancellation polls, and host publication stay
exactly as OPT-011. Cancellation still stream-synchronizes after each full
layer, including after a graph replay, then polls; a cancelled poll still
publishes nothing and must not enqueue later layers, logits, D2H, or scatter.

### sync_tokens and Engine production path

Add `SchedulerGraphs* graphs = nullptr` as the last optional argument of
`sync_tokens`. Pass it into `execute_prompt_chunk` and into the `chunk == 1`
`execute_token` call (decode FFN graphs on the `[4096, 1]` tail). Existing
native diagnostics keep the default `nullptr`.

`Session::sync` in `src/engine.cpp` passes `&impl_->graphs`. Production 128K
sessions therefore replay prompt FFN graphs on every full 4,096-row chunk and
decode FFN graphs on a one-row tail. This is CUDA-internal plumbing, not a
public ABI change.
