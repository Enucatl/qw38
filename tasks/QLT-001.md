against a predeclared, reproducible quality suite. Per the user-approved QLT-001
boundary amendment, the only newly generated external quality reference is the

## Implementation decisions

Extend the existing native high-level grammar with exactly one mode:

```text
qw38-eval MODEL --mode score --tokens CSV --continuation CSV --output DIR \
  --source-revision REVISION --source-state clean|dirty
```

`tokens` is the non-empty context and `continuation` is the non-empty
teacher-forced target. Their combined length must be at most 131,072. The
native path opens one authenticated Engine, creates one Session, synchronizes
the context once, and for each target reads the complete current FP32 logit row,
rejects any non-finite value, computes stable log-sum-exp and the target log
probability in double precision, records greedy and runner-up token IDs/logits
with lower-token-ID tie breaking, then atomically evaluates the target. It
publishes only a compact `qw38.eval-result` v1 `result.json`: exact context and
target token IDs/positions/frontiers, model/tool/runtime identities, per-target
log probability and top-two data, mean NLL, perplexity, and pass-neutral status.
No full logit blob is retained and the native executable never applies quality
thresholds. All request validation occurs before model open or output creation;
runtime or publication failure leaves no final directory. Existing mode schemas
and exit codes remain unchanged.

Add `ScoreRequest`, `ScoreStep`, and `ScoreResult` frozen annotated dataclasses,
a strict exact-key `read_score_result`, and `run_native` dispatch in
`tools/qw38_eval.py`. The reader recomputes mean NLL/perplexity from the retained
steps, validates token positions/frontiers, finite values, top-one ordering,
and identities, and rejects malformed or partial evidence.

Freeze the suite in `pins/quality_contract.json` and exact raw token sequences
in `fixtures/quality_inputs.json` before running Quartz. Input generation is a
deterministic, separately callable `tools/freeze_quality_inputs.py`; it accepts
a local copy of the WikiText-2 raw test parquet and the already pinned
`tokenizer.json`, verifies both hashes, and never downloads. Pin the dataset to
`Salesforce/wikitext` revision
`b08601e04326c79dfdd32d625aee71d232d685c3`, file
`wikitext-2-raw-v1/test-00000-of-00001.parquet`, LFS SHA-256
`5f1bea067869d04849c0f975a2b29c4ff47d867f484f5010ea5e861eab246d91`,
size 732,610 bytes, and its declared CC-BY-SA-3.0/GFDL license. Normalize no
text, concatenate non-empty rows with one newline in file order, and tokenize
without special tokens. Reproduction uses transient
`pyarrow==18.1.0`; it is not a runtime/test dependency.

The frozen input record contains these disjoint cases:

1. `wikitext_nll`: context token 0 and the following 1,024 targets from the
   test stream.
2. `continuation_2048`, `continuation_4096`, `continuation_6144`, and
   `continuation_8192`: 128-token contexts ending at the named offsets and the
   next 16 targets.
3. `recurrence_short` and `recurrence_long`: the same 128-target slice beginning
   at test-stream offset 20,480, preceded respectively by the immediately prior
   256 or 4,096 tokens. This isolates the additional error caused by a long
   hybrid recurrent/KV history while holding targets constant.
4. `retrieval_128k`: exact UTF-8 prefix
   `"Memorize this access code: 7391.\n"`, followed by WikiText test tokens
   starting at offset 32,768 and repeated in order as needed, followed by exact
   UTF-8 suffix
   `"\nQuestion: What access code were you told to memorize? Reply with the four digits only:\n"`.
   The freezer trims only from the distractor tail so prefix plus the tokenized
   target `7391` is exactly 131,072 tokens; it rejects a distractor whose decoded
   text contains `7391`. The needle begins at position 0. The target must decode
   exactly to `7391` with special-token skipping disabled.
5. Eight one-token multiple-choice task cases, each rendered through the pinned
   user-turn template with thinking disabled and ending `Reply with exactly one
   letter: A, B, C, or D.`. The exact user contents and answers are:

   - `What is 17 + 25?\nA. 41\nB. 42\nC. 43\nD. 44\nReply with exactly one letter: A, B, C, or D.` — `B`.
   - `What does this Python expression return: len("quartz")?\nA. 6\nB. 5\nC. 7\nD. 8\nReply with exactly one letter: A, B, C, or D.` — `A`.
   - `All quartz watches are timepieces. This object is a quartz watch. Which conclusion follows?\nA. It is not a timepiece.\nB. It might be a calendar.\nC. It is a timepiece.\nD. No conclusion follows.\nReply with exactly one letter: A, B, C, or D.` — `C`.
   - `How many minutes are in 3 hours?\nA. 60\nB. 120\nC. 240\nD. 180\nReply with exactly one letter: A, B, C, or D.` — `D`.
   - `Which list is in ascending numeric order?\nA. 9, 5, 2\nB. 2, 5, 9\nC. 5, 2, 9\nD. 2, 9, 5\nReply with exactly one letter: A, B, C, or D.` — `B`.
   - `Which option is a valid JSON object?\nA. {"x":1}\nB. {'x':1}\nC. {x:1}\nD. ["x":1]\nReply with exactly one letter: A, B, C, or D.` — `A`.
   - `Mira placed an amber key in the blue box. She placed a silver key in the red box. Which key is in the blue box?\nA. silver\nB. red\nC. amber\nD. blue\nReply with exactly one letter: A, B, C, or D.` — `C`.
   - `What number comes next: 2, 4, 8, 16, ?\nA. 18\nB. 20\nC. 24\nD. 32\nReply with exactly one letter: A, B, C, or D.` — `D`.

   The contract stores those byte-exact strings, option order, expected letter,
   rendered tokens, and expected single token ID; generation-time wording or
   option selection is forbidden.

Do not alter `tools/llama_authority/token_oracle.cpp`: its source hash is part of
the already admitted three-authority scalar fixture. Add the sibling
`tools/llama_authority/quality_oracle.cpp` and its CMake target instead. The new
adapter uses only pinned llama.cpp public APIs, loads the model once with every
layer on the GPU and tensor checking enabled, and consumes a versioned
little-endian request bundle generated from `fixtures/quality_inputs.json`.
The bundle contains, for each case, an ASCII case name, context count, target
count, then u32 context and target IDs. It rejects duplicate/unknown cases,
invalid counts or token IDs, trailing bytes, and any combined length above
131,072 before model execution.

The adapter creates a context sized to the largest reference case, uses explicit
positions and sequence 0, clears llama memory between cases, and submits chunks
of at most 512 tokens. It requests logits only at the context-final row and
subsequent teacher-forced target-predictor rows, computes stable double-precision
log-sum-exp from finite FP32 logits, uses lower-token-ID top-two tie breaking,
and writes a compact checked line protocol. `tools/run_llama_quality_reference.py`
verifies the exact llama contract, clean source checkout revision, model and
quality-input hashes, invokes that adapter once inside the existing pinned
llama authority image, strictly parses its output, and atomically writes
`fixtures/quality_llama_reference.json`.

The external reference contains exactly seven cases and no others:

1. `wikitext_nll`: all 1,024 target log probabilities and mean NLL;
2. `continuation_2048`, `continuation_4096`, `continuation_6144`, and
   `continuation_8192`: all 64 greedy/top-two results; and
3. `recurrence_short` and `recurrence_long`: all 256 target log probabilities,
   greedy/top-two results, and both mean NLL values.

These are the minimum external rows needed by the relative NLL, greedy, and
recurrence gates. The reference deliberately does not execute `retrieval_128k`
or the eight task cases: retrieval has an exact frozen answer plus an explicit
Quartz frontier requirement, and each task has an exact frozen answer token, so
running those through llama.cpp would add no reference datum used by acceptance.
A greedy near-tie is predeclared only when the llama.cpp top-one minus top-two
logit is at most `0.05`; the reference names the case, position, both token IDs,
both logits, and margin. The input/reference outputs are immutable before any
Quartz quality run; a failure cannot add an exception or change a threshold.

- greedy continuation: all 64 target positions equal the llama.cpp greedy token,
  except only a position already listed as a llama-reference near-tie may select its
  recorded runner-up; no post-run exception may be added;
- long-recurrence drift: short and long cases each satisfy perplexity ratio
  `<= 1.05`, all non-near-tie greedy targets match, and
  `(long_quartz_nll - long_llama_nll) -
  (short_quartz_nll - short_llama_nll) <= 0.02` nats;
- 128K retrieval: the final frontier is exactly 131,072, every target token is
  the greedy token with no near-tie exception, and decoding the target is exactly
  `7391`;
- task quality: all eight expected answer tokens are greedy top-one choices;
- global: reference and native records use the exact same model SHA-256; the
  reference uses the pinned clean llama.cpp revision/build, while all native
  records use the exact base revision, explicit dirty candidate-tree state,

### 2026-09-04 — 128K prefill architectural performance diagnostic

#### Executive root cause

The stopped run is not primarily a quality-harness or model-load problem. The
Quartz prompt path is a correctness-first chain of very small kernels. At long
context its dominant defect is the full-attention implementation: every prompt
token is dispatched separately, one CUDA block is used per query head, lane 0
serially computes the complete QK dot-product and softmax, and all six query
heads in a GQA group independently reread their shared KV history. That makes
the 16 full-attention layers quadratic in prompt length and gives the GPU very
little exploitable parallelism (`cuda/attention_decode.cu:112-179,248-294`).

The second large cost is projection dispatch. Quartz's prompt-specialized Q8_0
path launches a row-wise GEMV grid whose Y dimension is the number of prompt
rows, so it rereads the full weight matrix for each of the 64 rows rather than
sharing/tile-reusing weights across a genuine GEMM (`cuda/full_scheduler.cu:478-495`).
Q4_K/Q6_K do use a prompt tile, but only eight rows for this shape and without a
vendor/tensor-core GEMM (`cuda/quant_mmv.cu:235-240,328-362`). The fixed
64-token chunk then multiplies launch and synchronization overhead: the source
implies approximately 4,388 launches per full chunk, or 8.99 million launches
over 131,072 tokens, before 65,536 per-layer KV D2D copy commands and at least
one blocking commit/barrier per chunk (`cuda/full_scheduler.h:21` and
`cuda/full_scheduler.cu:1679-1990,2065-2077`).

GDN is also deliberately serial within each 64-token scan window, but its work
is linear in sequence length. It is a material low-occupancy cost across 48
layers, not the asymptotic explanation for the 128K collapse
(`cuda/gdn_step.cu:14,260-283`). The prompt path has no CUDA graph capture;
the existing graphs cover per-token decode FFNs only
(`cuda/full_scheduler.cu:720-750`; `docs/53-stable-address-cuda-graphs.md:39-61,111-117`).

The user's 8.6-hour stop and approximately 4.2 token/s figure are treated as a
user-reported observation, not a completed retained benchmark. There is no
128K Quartz result to admit. Moreover, the isolated production attention
fixture takes 0.871 seconds for one layer at position 131,071; naively
integrating that linear tail cost across 16 layers predicts about 254 hours.
That discrepancy means the stopped run's exact progress denominator, binary,
or workload timing boundary is unknown. It does not weaken the demonstrated
kernel defect, but it prevents using either 8.6 hours or 254 hours as a verified
end-to-end completion estimate.

The traffic and operation estimates use the actual GGUF inventory. Its
layer-projection weights comprise 9.626 GB Q4_K FFN, 5.908 GB Q8_0 GDN
projection, 1.248 GB Q8_0 attention projection, and 0.413 GB Q6_K attention
output. This is 24.351B logical matrix values per token, or 48.701 GFLOP/token.
For attention, `T(T+1)/2` at `T=131072` is 8,590,000,128. Multiplying by 16
layers and 12,288 FMA per context visit (24 heads x 256 dimensions for QK plus
V) gives 1.689 quadrillion FMA, or 3.378 PFLOP. The same unreused BF16 K+V
geometry gives about 3.378 PB of logical reads. Projection plus attention is
therefore about 9.76 PFLOP and 4.48 PB of source-derived work/traffic. If the
user-reported 8.6 hours represented equivalent completed work, those totals
would imply only about 315 GFLOP/s and 145 GB/s effective rates, consistent
with severe serialization and poor reuse. This conditional calculation is not
a completion-time claim.

At layer granularity, every layer performs about 0.535 GFLOP/token of dense FFN
projection. Each GDN layer adds about 0.232 GFLOP/token of GDN projection; each
attention layer adds about 0.210 GFLOP/token of Q/K/V/output projection, before
its history-dependent attention. Compressed weight storage is approximately
150.4 MB of FFN per layer, plus 123.1 MB per GDN layer or 103.8 MB per attention
layer. Under the actual prompt dispatch, a full 64-row chunk logically rereads
about 9.08 GB of projection weights per GDN layer and 6.40 GB per attention
layer. Launch accounting for that same full chunk is 20 kernels per GDN layer
and 210 per attention layer: the latter includes 192 attention kernels (three
per token). Adding 65 embedding/conversion launches and three final-output
launches gives 4,388. These are static source counts, not profiler-attributed
durations; optional cancellation polling would add a device synchronization
after every layer, but the ordinary score path does not enable that callback.
