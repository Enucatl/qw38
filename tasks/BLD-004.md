## Goal and boundaries

Every CUDA target compiled with `QW38_DIAGNOSTIC_TRACE` uses scheduler-owning and
checkpoint objects compiled with the same definition. The affected native
diagnostics consequently allocate and report the existing 81,920-byte trace-tap
workspace, making their observed prompt, atomic, and post-graph memory values
equal the already checked-in expectations.

- Constraints: preserve CUDA 13.0.2, `sm_120`, C++17, no exceptions/RTTI, release/diagnostic trace isolation, the existing 131,072-token allocation model, and the PIN-004 rule that routine local-source hashes do not return to feature contracts.
- Non-goals: changing scheduler allocation formulas, trace tap count or shapes, production/release linkage, semantic CUDA execution, frozen fixtures, measured handbook claims, OPT-005 implementation/evidence, release provenance generation, or `plan.md`.
- Plan impact: `none`
- Affected interfaces: internal Make target/object graph only; no public API, file format, fixture schema, or command-line behavior changes.

## Implementation decisions

Change only the diagnostic object graph and add a host-side regression assertion
for it.

1. In `Makefile`, add a diagnostic CUDA engine object compiled from
   `src/engine.cpp` with both `QW38_CUDA_RUNTIME` and
   `QW38_DIAGNOSTIC_TRACE`. Use it in `CUDA_DIAGNOSTIC_ENGINE_OBJECTS`; keep
   `$(CUDA_BUILD_DIR)/engine.o` unchanged for every release product.
2. In `Makefile`, add `checkpoint.trace.cuda.o`, compiled from
   `cuda/checkpoint.cu` with `QW38_DIAGNOSTIC_TRACE`. Link it into the CUDA
   diagnostic eval product and the checkpoint and timing diagnostics. Keep
   `checkpoint.cuda.o` in all release products.
3. Replace `full_scheduler.cuda.o` with `full_scheduler.trace.cuda.o` in exactly
   the prefix-sync, prompt-scheduler, atomic-eval, checkpoint, memory-fit, and
   timing diagnostic targets. Their source recipes already define
   `QW38_DIAGNOSTIC_TRACE`; do not change their source files or arithmetic.
4. Extend `tests/test_cuda_trace.py` with a Makefile object-graph test that
   extracts the relevant target declarations and proves: all six diagnostic
   consumers link the trace scheduler and reject the ordinary scheduler;
   diagnostic eval uses the trace engine, trace checkpoint, and trace scheduler;
   checkpoint/timing use the trace checkpoint; and representative release eval
   continues to use only ordinary engine/checkpoint/scheduler objects.
5. Do not edit pin or fixture JSON. PIN-004 removed routine source hashes, and
   the accepted atomic/prompt/memory fixtures already contain the correct
   diagnostic byte totals. Do not edit handbook chapters because their current
   numeric claims already agree with those fixtures.
6. Do not repair `cuda/attention_decode.cu` under BLD-004. The repeated full-suite
   failure is an ordinary regression introduced by the blocked OPT-005 baseline,
   outside BLD-004's object-graph acceptance and changed-file boundary. The
   minimum source repair is one expression: in `stage_chunk_rows`, change the
   one-row diagnostic write from `normalized_key[lane]` to
   `normalized_key[base + lane]`. That repair may proceed only after the
   coordinator gives it ledger ownership by registering a stable regression task
   (or another explicit workflow-authorized recovery boundary) and links that
   owner here. Do not repin the attention fixture or weaken/skip the full CUDA
   gate.
