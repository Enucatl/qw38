# OPT-008 — Make 4,096 tokens the default prompt chunk

## Control

- Primary ID: `OPT-008`
- Coupled IDs: `none`
- Dependencies: `OPT-007`, `MEM-002`; both done at planning admission
- Status: `done`
- Ledger acceptance: Default prefill chunks are 4,096 tokens with bounded fallback for tails/capacity; atomic commit, cancellation, and 128K reserve gates pass

## Goal and boundaries

Make 4,096 rows the production prompt-chunk policy while bounding each
workspace's prompt allocation and dispatch limit by its session capacity. A
prompt suffix of 4,097 rows must execute as `[4096, 1]`; a session whose total
capacity is below 4,096 must allocate and execute no more prompt rows than that
capacity. Preserve exact state/output equivalence, whole-chunk publication,
layer-boundary cancellation, the internal 64-row GDN scan, the admitted
two-query-row attention kernel, and the 131,072-token memory reserve.

- Constraints: keep C++17, CUDA 13.0.2, `sm_120`, the exact pinned Qwen3.8
  model, BF16 activation/KV storage, FP32 residual and recurrent state, the
  existing public `Engine`/`Session` API, and all frozen numeric gates. Prompt
  scratch remains one reusable fixed allocation per workspace: its row count is
  `min(4096, capacity)`, never the request length and never the full 128K
  session capacity. A failed or cancelled chunk publishes no GDN state, KV
  rows, tokens, last outputs, or frontier. The full 128K owner set, allocator
  delta, and uploaded graphs must still leave at least 1,610,612,736 bytes free.
  Do not edit `Makefile`; its existing prompt-scheduler, atomic-eval, and
  memory-fit targets cover the required native diagnostics.
- Non-goals: changing the 64-row internal GDN scan (`OPT-013`); changing prompt
  MMQ kernels or their tile selection (`OPT-009`); changing KV layout
  (`OPT-010`); adding prompt fusion/overlap (`OPT-011`) or prompt CUDA graphs
  (`OPT-012`); changing attention block ownership admitted by OPT-007; changing
  checkpoint or public API formats; loosening exact/numeric gates; claiming a
  comparative or release-level speedup; or executing the 128K retrieval gate.
- Plan impact: `none`
- Affected interfaces: the CUDA-internal constant `kPromptChunkRows` changes
  from 64 to 4,096, and `SchedulerWorkspace` gains an internal effective
  prompt-row capacity used for allocation, validation, dispatch, and candidate
  strides. No public engine, CLI, server, checkpoint, model, or JSON API changes.
- Implementation classification: not mechanical. The change expands persistent
  device scratch by about 1.60 GiB at production capacity and changes atomic
  transaction size, cancellation duration, attention candidate addressing,
  and the physical 128K memory ledger.

## Implementation decisions

Keep `kPromptChunkRows` as the compile-time policy constant and change its value
to 4,096. Add `prompt_chunk_rows_` to `SchedulerWorkspace`; during `create`, set
it to `min(kPromptChunkRows, capacity)` before prompt allocation. Allocate all
prompt residual, normalization, Q8, projection, mixer, GDN-intermediate, and
all-layer attention candidate buffers with that effective row count. Reset it
to zero in release and transfer/reset it in move operations with the other
workspace ownership fields.

Make `execute_prompt_chunk` reject `token_count` above
`workspace->prompt_chunk_rows_`. Use `prompt_chunk_rows_ *
internal::kAttentionKvWidth` as the candidate K/V layer stride for both prepare
and commit. Make `sync_tokens` choose `min(workspace->prompt_chunk_rows_,
remaining)`; retain the existing one-row `execute_token` fallback. Because
workspace and session capacities must already match, this implements both
request-tail and capacity fallback without a second configuration source.

Retain the GDN launcher's internal 64-row scan windows and the OPT-007 attention
kernel unchanged. A 4,096-row outer transaction therefore reuses current
arithmetic and advances GDN candidate state across 64 internal windows while
attention sees the full causal outer chunk. Publication remains after all 64
layers, final output, candidate KV copies, and device synchronization.

Replace the prompt-scheduler diagnostic's old 65-versus-tokenwise speed gate
with direct acceptance evidence:

1. Run a deterministic 4,097-row `sync_tokens` call and require it to report
   4,097 evaluated rows and finish at frontier 4,097.
2. Build an independent same-capacity reference by calling
   `execute_prompt_chunk` in 64-row pieces and `execute_token` for the final
   row; require byte-exact full session state, last hidden, and logits. This
   retains the admitted 64-row boundary as the differential reference without
   the prohibitive repeated-token scheduler.
3. Count non-cancelling layer polls on a capacity-65 session and require exactly
   64 polls for 65 rows, proving one capacity-bounded prompt transaction rather
   than `[64, 1]`; compare it byte-for-byte with an explicit `[64, 1]`
   same-capacity reference.
4. Cancel a 4,096-row chunk at a deterministic synchronized layer boundary and
   require cancelled status, frontier zero, unchanged caller outputs, and
   byte-exact state equality with an empty same-capacity reference.
5. Assert the effective row allocation and exact requested workspace bytes for
   capacity 3, 65, 4,097, and 131,072. In the required diagnostic build, whose
   workspace includes the 81,920-byte trace allocation, the exact totals are
   161,595,680; 186,711,136; 1,819,620,960; and 1,831,810,560 respectively.

Derive workspace bytes from the allocation sites rather than from a delta
against one historical capacity. For session capacity `C` and effective prompt
rows `R = min(4096, C)`, the required diagnostic build has

`workspace_bytes(C) = 160,380,416 + 96*C + 404,992*R`.

The `96*C` term is the FP32 decode attention-score allocation
`24 * C * sizeof(float)`. The prompt-row coefficient is exactly 404,992 bytes:
40,960 residual A/B; 10,240 BF16 normalized; 34,816 BF16 projected; 19,584
Q8 blocks; 139,264 projection A/B; 8,192 projection C/D; 20,480 mixer output;
384 GDN decay/update; 40,960 GDN convolved; 24,576 GDN recurrent output; and
65,536 all-attention-layer candidate K/V. The fixed 160,380,416 bytes cover all
remaining device allocations, including the diagnostic trace taps. A release
build without `QW38_DIAGNOSTIC_TRACE` is exactly 81,920 bytes smaller, but the
prompt-scheduler, atomic-eval, and memory-fit acceptance binaries intentionally
link `full_scheduler.trace.cuda.o` and therefore use the diagnostic totals. At
capacity 131,072 the corresponding non-trace production binary would report
1,831,728,640 bytes; that number is explanatory and is not the memory-fit
fixture's acceptance value.

The superseded 425,472-byte coefficient double-counted one 5,120-element FP32
residual row (20,480 bytes). Applying that incorrect coefficient to historical
64-row totals also obscured the independent `96*C` score term; the planned
capacity-4,097 value additionally contained a 608-byte arithmetic transcription
error. The three live results are mutually consistent with the source-derived
formula: 161,595,680 at capacity 3, 186,711,136 at capacity 65, and
1,819,620,960 at capacity 4,097.

At production capacity 131,072, changing 64 prompt rows to 4,096 adds
`4032 * 404,992 = 1,632,927,744` bytes to the recorded 198,882,816-byte
diagnostic workspace, yielding 1,831,810,560 bytes. Holding only the other
recorded owner and allocator values constant predicts 29,560,766,304 explicit
Quartz bytes, 3,566,174,208 free bytes, and a 1,955,561,472-byte margin above
the 1.5 GiB requirement. These are planning arithmetic only: the checked-in
fixture and documentation must use the fresh pinned diagnostic's actual
allocator delta, free memory, UTC, and host RSS and must fail if the exact owner
equation or reserve comparison is false.

Update the existing SCH-002 prompt contract/fixture to identify both SCH-002
