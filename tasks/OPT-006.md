# OPT-006 — Reuse tiled KV loads across grouped query heads

## Control

- Primary ID: `OPT-006`
- Coupled IDs: `none`
- Dependencies: `OPT-005`; done at planning admission
- Status: `in_progress`
- Ledger acceptance: Each shared KV head is loaded once per tile for its six query heads; exact GQA outputs pass and measured KV traffic falls

## Goal and boundaries

Change the production tiled prompt-attention block from one `(query head, query
row)` owner to one `(KV head, query row)` owner. Each block must load a causal
K/V tile once into shared memory and reuse it while evaluating all six query
heads mapped to that KV head. Preserve the current online-softmax arithmetic,
candidate/committed visibility, two-kernel chunk launch, and exact observable
results. Retain the current per-query-head tiled kernel as a diagnostic reference
and measure executed K/V global-load requests for both paths.

- Constraints: keep C++17, CUDA 13.0.2, `sm_120`, 256 threads, 32-context
  tiles, the production `24 / 4 = 6` GQA mapping, token-major inputs/outputs,
  BF16 K/V storage, FP32 normalization/score/softmax/value accumulation,
  partial 64-lane RoPE, strict chunk causality, prepare/commit isolation, and all
  frozen ATN-001/ATN-002/OPT-005 numeric limits. The production launcher must
  remain two kernels for every positive chunk size and must not allocate a new
  persistent or prompt-sized workspace. Do not edit `Makefile`, whose complete
  bytes are pinned by historical contracts; build the new diagnostic with an
  explicit pinned `nvcc` command, as OPT-005 does.
- Non-goals: assigning multiple query rows to one block (`OPT-007`), changing
  the 64-row scheduler chunk (`OPT-008`), changing the physical KV layout
  (`OPT-010`), changing projections or output fusion, prompt CUDA graphs,
  changing decode/cache/checkpoint formats, proving physical DRAM transactions,
  or claiming scheduler/end-to-end throughput recovery.
- Plan impact: `none`
- Affected interfaces: no public engine, CLI, server, model, checkpoint, or
  fixture-format interface changes. Add CUDA-internal diagnostic launchers for
  the retained per-query-head tiled path and instrumented grouped path; keep all
  existing production launcher signatures and validation behavior unchanged.
- Implementation classification: not mechanical. This work changes a CUDA
  kernel, CUDA thread/block concurrency and synchronization, shared-memory tile
  ownership, and numerical invariants, and designs new acceptance evidence for
  executed K/V load traffic. It does not cross a security boundary or change
  host/persistent memory ownership.

## Implementation decisions

Keep `stage_chunk_rows` unchanged. Rename the current
`tiled_chunk_attention` implementation to make its per-query-head diagnostic
role explicit and retain it byte-for-byte apart from optional load-count
instrumentation. Implement the production grouped kernel with grid
`(config.kv_heads, token_count, 1)`. A block owns one absolute query row and one
KV head, and handles query-head indices
`kv_head * group_size ... (kv_head + 1) * group_size - 1`.

Each thread holds one normalized query lane and one FP32 value accumulator per
query head in the group. Use a single 256-float shared scratch array to preserve
the current serial, increasing-lane RMS and dot-product reductions: normalize
and apply RoPE to each group query head in turn, saving its lane in registers;
for each causal 32-row tile, load each BF16 K/V lane exactly once into shared
memory; for each row and group query head, write lane products to the shared
scratch, have lane zero sum indices `0..head_width-1`, and update that head's
running maximum and denominator in context order. Every lane updates the six
value accumulators from the same shared V row. After the final tile, apply the
existing stable sigmoid gate and write each group head's token-major FP32
output. Preserve the one-row writes to `normalized_query` and the unchanged
staging write to `normalized_key`.

Compile the grouped and retained per-query kernels from templates with
instrumentation disabled for ordinary launches. Add internal diagnostic
launchers named
`launch_attention_prepare_chunk_grouped_instrumented` and
`launch_attention_prepare_chunk_per_query_tiled_reference`. They take the same
arguments as `launch_attention_prepare_chunk` plus a non-null device
`std::uint64_t* kv_load_values` counter, apply the same fail-closed validation,
run the unchanged staging kernel, and launch their respective instrumented
attention kernel. In each attention block, every thread increments a local
counter immediately alongside each actual global K and V source load and
atomically contributes once after the final tile. The counter therefore records
executed BF16 K/V values requested by the kernel, not a source-derived fixture
constant. Initialize it to zero outside the launcher. The production launcher
uses the non-instrumented grouped specialization and has no counter branch or
atomic overhead.

Add a standalone `cuda/gqa_attention_test.cu`. For production shape
`{24, 4, 256, 64, 131072}`, independently allocate grouped, retained-per-query,
and untiled-reference buffers. Cover row counts 1, 3, 9, and 64 across both a
partial first tile and a multi-tile committed prefix. Require grouped versus
retained-per-query output bytes to be exact, candidate K/V bytes exact,
finite output, unchanged committed caches/frontier during prepare, exact
commit/frontier behavior, future committed-row and later candidate-row
exclusion, untouched global score scratch, unchanged invalid-input rejection,
and two captured kernel nodes. Also compare grouped output to the untiled
reference under the existing OPT-005 max-absolute/RMS/cosine limits.

For traffic cases at committed prefixes 2,048, 8,192, and 32,768 with 64 query
rows, execute each instrumented tiled path from independently seeded buffers
and copy its device counter to the host. Let
`contexts = sum(start_position + token + 1 for token in [0, token_count))`.
Require the retained counter to equal
`query_heads * contexts * head_width * 2`, the grouped counter to equal
`kv_heads * contexts * head_width * 2`, and retained/grouped to equal the
production group size `6`. Record value counts and byte counts (value count
times `sizeof(__nv_bfloat16)`) in one measured RTX 5090 fixture. This is
executed global-load-request evidence and must be described explicitly as not a
hardware DRAM-transaction measurement.

Add one schema-1 task contract and one atomic fixture regeneration/validation
module. The shared Python validator must require exact keys/types, production
shape and toolchain metadata, all true semantic predicates, exact output
comparisons, frozen untiled-reference metrics, all three traffic cases, the
closed-form expected counters above, exactly 6x lower grouped requested values
and bytes, and a proof-limit string that excludes physical DRAM and end-to-end
claims. Its negative test must reject at least a missing predicate, a grouped
counter off by one, a ratio other than six, a byte/value inconsistency, and
placeholder metadata. The exclusive test builds and runs the native diagnostic,
parses exactly one result, and passes it through the same validator used for the
checked-in fixture. `--regenerate-fixture` performs exactly one successful
pinned run and atomically replaces the fixture.

Update the existing attention-prefill chapter with the grouped block mapping,
barrier/shared-memory ownership, counter formula, measured fixture values, and
proof boundary. Add the local-derivation/evidence entry to `docs/sources.md` and
one final OPT-006 row to the documentation audit. Do not create an EDU task:
the already-authoritative attention chapter is the inseparable documentation
surface, while a new educational ledger increment is not required for this
narrow optimization.
