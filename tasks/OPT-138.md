# OPT-138 — Profile remaining short-decode and prefill excess versus llama

Status: pending. Dependencies: OPT-136, OPT-137. Coupled IDs: none.
Priority: P1. Plan impact: none. Diagnostics only. This supplies the profiler
needed for items 3 and 4 of the 2026-09-14 investigation plan; it does not
implement another kernel or promise a new optimization ladder.

## Outcome

On the accepted stack left by OPT-137 (kept candidate or retained parent),
produce independently verified rankings of remaining D128/D2048 decode and
P4096 prefill excess versus the pinned llama engine. Explain the largest gaps
with targeted hardware counters and real-input replay. Deliver exactly one
bounded next-experiment specification per phase when the evidence permits;
otherwise state the missing evidence instead of inventing an optimization.

Ledger acceptance: Current matched D128/D2048/P4096 profiles reconcile whole
time, fused families and overhead; targeted counters/replays yield supported
decode/prefill priorities or explicit unknowns without changing production.

## Matching and ranking rules

Produce per-run raw counts and a disjoint logical-family table for each phase.
Use OPT-136 families, separating prompt MMQ from decode MMV and preserving
conversion, staging, epilogue and commit/copy ownership. llama fused operations
define enclosing groups; regroup Quartz to that boundary. Expose unmatched
time explicitly, not zero. Column set:

`family`, `logical_members`, `inputs/shapes/dtypes/strides`, `Quartz_ms`,
`llama_ms`, `delta_ms`, paired uncertainty, `share_of_whole`, `overlap_ms`,
`kernel_ids`, `coverage_status`, `proof_limit`.

Show whole wall gap = matched disjoint family excess + unmatched work gap +
scheduling/host residual, with uncertainties and synchronization overlap.
Absolute residual above 5% of Quartz wall stops a complete ranking claim and
requires one bounded mapping/window diagnosis. Do not distribute unexplained
time proportionally across families. A parent graph is not an additional family
on top of its kernel children. CPU launch/sync spans cannot be added to GPU
durations that occur concurrently.

Select at most two families per phase for deeper investigation. For decode,
rank by the larger positive excess across D128/D2048; select each family only
once. For prefill, rank by P4096 excess. Require a positive lower confidence
bound on a matched excess before labeling it evidenced; otherwise report
ranking uncertainty. Break exact ties by family name. No hand-picked GDN or
Q8 priority if another family has a larger supported excess.

Use OPT-136's paired-difference confidence calculation: three independent
capture repetitions, one-sided 95% Student-t lower bound with df=2; tokens and
layers are not independent replicates. For a decode family's top-two selection
use its middle window [122,134) at each prefix; early/late windows are required
consistency checks and are reported separately. If only early/late appears to
win, label the ordering unstable rather than selecting the best window. P4096
uses complete-prompt totals from its three capture repetitions. This fixes the
ranking input before examining results.

## Targeted counters and replay

For each selected family choose its largest-duration Quartz kernel and matched
llama kernel (at most four families x two engines = eight kernels). For a fused
match use the enclosing fused kernel and explicitly state the comparison limit.
One real input capture per selected shape, one counter collection per kernel;
one diagnosed retry only. Retain actual production weights and corresponding
activations, not random synthetic values presented as production evidence.

Use installed Nsight Compute `--query-metrics` first. Query only supported names
for DRAM read/write bytes and throughput, L2 traffic/hit behavior, tensor/SM
throughput, achieved occupancy/active warps, long-scoreboard/barrier stalls,
registers and local-memory spills. Save exact selected names, values, units,
replay mode and target kernel identity in `counter-evidence.json`. Unsupported
metrics or permission failures are null with the tool error, never zero. Do
not install tools, change driver profiling permissions or run privileged
commands as an implicit workaround.

Counter replay perturbs cache/runtime. Correlate it with the production-node
trace and a complete-family replay: one warmup + three alternating paired
rounds rotating across all applicable layers/weights; use existing actual
activations and include staging/conversion/output costs. This is diagnostic
screen evidence, not a keep. Record cache residency and input rotation; do not
extrapolate one repeatedly cached matrix across 64 layers.

For the report, use these interpretation rules:

- Bandwidth limitation needs observed byte/throughput evidence and a matched
  explanation of transactions/reuse. Listed 1792 GB/s peak is not measured
  sustainable bandwidth; bytes/peak is not a savings upper bound.
- A serial reduction, low occupancy, bank conflict or expensive unpack is a
  hypothesis until source/SASS and the targeted measurement support it.
- For GDN, explicitly distinguish unchanged FP32 state traffic from arithmetic,
  parallel decomposition and surrounding projection cost. Reconcile any
  recurrence-only win/enclosing loss as seen in OPT-109.
- For Q4/Q8/Q6, include quantization/staging and output consumers. OPT-110's
  source-faithful Q4 adapter is already shipping; do not propose porting it again.
- For fusion, count device kernel nodes/dependencies and intermediate work
  inside graphs. OPT-131's assumed traffic estimate cannot prove all such
  savings zero. A measured small bound remains a valid reason to deprioritize.
- For prefill, quantify prompt MMQ, GDN and attention shares and their matched
  excess; do not attribute the whole ~4% historical deficit to one kernel by
  analogy with decode.
