# OPT-010 — Tile KV layout for coalesced exact GQA access

## Control

- Primary ID: `OPT-010`
- Coupled IDs: `none`
- Dependencies: `OPT-007`, `SES-003`; both done at planning admission
- Status: `done`
- Ledger acceptance: KV storage supports coalesced tile loads without changing logical values, checkpoint compatibility, prefix reuse, or capacity

## Goal and boundaries

Change production committed BF16 K/V storage from token-major
`[token][kv_head][lane]` to head-major token-contiguous
`[kv_head][token][lane]` so each GQA 32-context tile for one KV head is one
contiguous device region. Keep every logical `(token, kv_head, lane)` BF16
value identical, keep the SES-003 on-disk checkpoint bytes/layout hash
unchanged by packing and unpacking at the file boundary, keep exact token-ID
prefix reuse, and keep the 16-layer 8 GiB allocation
(`16 × 131072 × 1024 × 2 × 2` bytes). Candidate chunk rows stay token-major.
Production GQA outputs remain byte-exact to the retained one-row grouped path.

- Constraints: keep C++17, CUDA 13.0.2, `sm_120`, `--fmad=false`, 256 threads,
  32-context K/V tiles, the production `24 / 4 = 6` GQA mapping, token-major
  Q/K/V/gate inputs and attention outputs, BF16 K/V values, FP32
  normalization/score/softmax/value accumulation, partial 64-lane RoPE, strict
  causality, prepare/commit isolation, two production attention kernel nodes
  per positive chunk, fixed 33,792 dynamic shared bytes, and all frozen
  ATN-001/ATN-002/OPT-005/OPT-006/OPT-007 numeric and exact-state gates. Do not
  add a persistent session, workspace, or prompt-sized allocation. Do not edit
  `Makefile`; build the new diagnostic with an explicit pinned `nvcc` command.
  Checkpoint magic `QW38CKP1`, version `1`, header size `248`, model hash, and
  layout hash `b816f20fc25c3de29b71e0404a3b7ef829142e7ad41aad0d67bcfbb92c7550fd`
  stay byte-identical. Exclusive RTX 5090 work stays serialized.
- Non-goals: claiming DRAM-transaction, Nsight, latency, throughput, or
  end-to-end speedup evidence; changing candidate-row layout; changing scalar
  CPU KV layout; bumping checkpoint version or layout hash; adding paged/block
  tables; fusing prompt execution (`OPT-011`); prompt graphs (`OPT-012`); GDN
  scan parallelism (`OPT-013`); loosening frozen envelopes; editing `plan.md`
  or `QLT-001`; changing the 4,096-row prompt chunk or MMQ tiles.
- Plan impact: `none`
- Affected interfaces: no public Engine, CLI, server, model, or JSON API
  changes. CUDA-internal committed KV addressing, commit scatter, checkpoint
  pack/unpack, and `SchedulerSession::state_equals` committed-KV comparison
  change. The on-disk checkpoint section order and logical token-major KV
  payload remain the SES-003 contract. New schema-1 contract and fixture files
  are task evidence, not a public protocol.
- Implementation classification: not mechanical. This changes CUDA KV
  addressing, tile-load pointer identity, commit scatter, checkpoint
  conversion, session equality, and exact BF16/numeric invariants. Use the
  CUDA/numeric implementation agent, not a mechanical path.
- Documentation stage: required. Update the existing attention-decode,
  attention-prefill, and checkpoint handbook chapters plus `docs/sources.md`
  and one non-final then final OPT-010 audit row. Do not add an EDU task;
  EDU-030 and EDU-035 already cover those chapters.

## Implementation decisions

Keep candidate K/V token-major:
`candidate[rel_token * kv_heads * width + kv_head * width + lane]`. Staging
(`stage_chunk_rows` and the decode `normalize_key_and_stage_value` path)
continues to write that layout. Q/K/V/gate inputs and attention outputs stay
token-major.

Store committed K/V as head-major token-contiguous:

```text
physical(token, kv_head, lane) =
    (kv_head * capacity + token) * head_width + lane
```

For production `capacity = 131072` this is identical to packing 32-token tiles
as `[kv_head][tile_id][row_in_tile][lane]` because `131072 % 32 == 0`. The
open formula needs no padding, so test capacities such as 3 remain legal and
the 8 GiB product does not grow. Logical token-major index, used by
checkpoints and candidates, remains:

```text
logical(token, kv_head, lane) =
    token * kv_heads * head_width + kv_head * head_width + lane
```

Add `__host__ __device__` inline helpers in `cuda/attention_decode.h`:

- `kAttentionKvTileRows = 32`
- `attention_kv_logical_index(...)`
- `attention_kv_physical_index(...)`
- `attention_kv_tile_base_offset(kv_head, tile_start, capacity, head_width)`
  equal to `physical(tile_start, kv_head, 0, ...)`

`attention_cache_values` stays `kv_heads * head_width * capacity`.

Every committed-cache reader uses the physical helper: the production
`two_row_grouped_tiled_chunk_attention` kernel, the retained
`one_row_grouped_tiled_chunk_attention` and `per_query_tiled_chunk_attention`
kernels, and the untiled `grouped_attention` reference. Candidate readers keep
the existing token-major formula. For a committed tile whose 32 (or fewer tail)
rows all lie below `start_position`, the production kernel obtains one
`tile_base` pointer and loads:

```text
keys[row * kMaximumHeadWidth + lane] = tile_base[row * width + lane]
values[row * kMaximumHeadWidth + lane] = tile_base_v[row * width + lane]
```

That global span is `rows * width` consecutive BF16 values. Mixed tiles (some
committed rows, some candidate rows) load committed rows from the corresponding
physical addresses and candidate rows from token-major candidate storage; they
are not claimed as one coalesced region. Shared-memory layout, online-softmax
order, two-row ownership, and 33,792 dynamic shared bytes stay as OPT-007.

Rewrite `commit_rows` to scatter each candidate token-major value into
`physical(start_position + rel_token, kv_head, lane)`. Pass `capacity` and
`head_width` into the kernel; the current `target = start_position * row_values`
contiguous copy is wrong after the layout change. Keep the existing
synchronize-then-publish-frontier behavior for the attention-unit commit
launchers.

Replace production scheduler KV `cudaMemcpyAsync` slabs in decode commit and
prompt-chunk commit with `launch_attention_commit_chunk` per attention layer,
using a per-layer dummy device frontier pointer or a dedicated scatter-only
entry that does not publish `SchedulerSession::frontier_`. Session frontier
publication remains the existing host `++frontier_` /
`frontier_ += token_count` after all 16 layers and GDN pointer swaps. Do not
advance a device session frontier from the attention kernel. Preferred API:
add `launch_attention_scatter_chunk(...)` with the scatter body and no frontier
store; keep `launch_attention_commit_chunk` as scatter plus frontier store for
existing attention diagnostics.

Change `SchedulerSession::state_equals` so each layer/head compares the
contiguous physical span
`attention_key_ + layer * cache_stride + kv_head * capacity * kAttentionHeadWidth`
for `frontier_ * kAttentionHeadWidth * sizeof(__nv_bfloat16)` bytes (same for
values). Do not compare the first `frontier_ * kAttentionKvWidth` bytes of a
layer.

Checkpoint save/restore keep the on-disk logical token-major prefix. Add
`launch_pack_committed_kv` and `launch_unpack_committed_kv` in
`cuda/attention_decode.cu` / `cuda/attention_decode.h`. Save, per layer, packs
`[0, frontier)` into a transient device staging buffer of at most `kChunkBytes`
(1 MiB, 512 tokens) and `write_device`s that staging buffer. Restore reads into
the same staging buffer and unpacks into physical addresses. Allocate and free
that staging buffer inside save/restore; do not add it to the session or
workspace. Magic, version, hashes, section sizes, and the two-token
160,004,416-byte SES-003 file size stay unchanged when logical state is
unchanged. Do not bump `kLayoutSha256`.

Host attention diagnostics that currently fill or read committed cache as a
token-major vector must convert at the HtoD/DtoH boundary so logical
`(token, head, lane)` values stay the pre-change pattern. Provide a small host
helper in the tests or as header inline loops over
`physical_index`/`logical_index`. Do not regenerate OPT-005/OPT-006/OPT-007
fixtures unless an inherited predicate fails after logical-preserving
conversion; the intended result is that those fixtures remain valid.
