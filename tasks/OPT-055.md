# OPT-055 — Capture measured remaining launch overhead

Status: pending. Dependencies: OPT-054. Supersedes pending OPT-031.
Primary target: D2048, plus P only where profiling justifies prompt capture.
Read [the shared protocol](PERFORMANCE-RECOVERY-2026-09-10.md).

## Scope and decision

Revisit OPT-043 launch/wait attribution after the compute tasks. Old OPT-031
would capture exact-4096 mixer/GDN beside FFN graphs without first knowing the
remaining benefit. This task covers that work at the **selected** internal batch
size and additionally addresses decode coverage. If CPU submission gaps are
below measurement noise, record a no-change result with evidence; do not build
graphs for an assumed speedup. Compare public Session/server cancellation-enabled
execution as well as the bare kernel oracle, since a non-null poll callback
currently permits per-layer `cudaDeviceSynchronize`.

## Implementation if justified

Extend `SchedulerGraphs` in `cuda/full_scheduler.{h,cu}` with stable-address
decode layer segments containing mixer/projections/core/FFN, then benchmark
larger segments up to a full token. Put changing token/position/frontier values
in a preallocated device parameter block. For context-dependent grid sizes use
small bounded position buckets or node parameter updates; do not allocate a
graph for every context position or process all 128K KV for a short token.

Keep D2H logits, successful state publication, and cancellation decisions outside
the captured candidate computation. Select bounded segments when full-token
capture violates existing cancellation latency. Avoid CUDA synchronization at
every layer when polling can occur at a safe already-completed segment boundary;
do not remove cancellation or publish partially completed state. Preserve
errors, timeouts and explicit stream/event dependencies.

For prompt, capture stable mixer/GDN work only at OPT-054's selected physical
batch size; keep candidate KV indexing/position updates correct. Start with
reuse of selected-shape FFN graphs. No generic graph framework. References:
pinned llama `ggml/src/ggml-cuda/ggml-cuda.cu` graph machinery and ds4
`ds4_cuda.cu` `g_decode_graph_stream` capture,
launch and invalidation logic. Dynamic model policies in ds4 are out of scope.

## Acceptance

Require graph/eager equality within the same arithmetic path; prompt/decode
cross-path quality is already covered by OPT-044. Test token changes, cache
frontier growth, reset/restore, partial tails, graph invalidation, cancellation
at each admitted boundary and injected failure before publication. Count graph
nodes/launches and measured idle/waits; include parameter uploads, graph update
and D2H costs in timing. Exclude initial capture only where the frozen protocol
already creates graphs before timing; report first-request setup separately.
Update allocation ledger and verify 128K post-graph reserve.
Add task contract/fixture, `tests/test_opt055_execution_graphs.py`, and
`evidence/optimization/opt055-execution-graphs/`. Run new host/native test,
`tests/test_cuda_graph.py`, `tests/test_cuda_prompt_graph.py`,
`tests/test_cuda_atomic_eval.py`, `tests/test_cuda_prefix_sync.py`,
`tests/test_cuda_checkpoint.py`, `tests/test_cuda_memory_fit.py`,
`tests/test_server.py`, and shared P/D acceptance.
