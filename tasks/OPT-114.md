# OPT-114 — Calibrate the fresh sitting and measure real decode launch overhead

Status: pending. Dependencies: OPT-106. Coupled IDs: none.
Primary target: measurement validity and conditional decode-graph opportunity.

## Outcome

Establish a fresh same-binary Quartz A/A control and determine whether decode
launch gaps are large enough to justify the existing eight-layer segment-graph
path. This is a diagnostic and measurement task; it adds no production
selector or graph path by itself. It replaces the use of historical OPT-098
samples as a causal control and prevents the `other_idle` residual from being
misread as GPU idle.

## Evidence and rationale

OPT-106 reports selected Quartz equal to the post-098 combination, but its
current D128 result (53.50 tok/s) differs substantially from the historical
OPT-098 control fixture (37.29 tok/s). `tools/opt106_batch_gate.py` loads those
historical arrays for the internal-improvement interval. That is valid history,
not a same-sitting A/A control for new tasks.

The existing decode attribution computes `other_idle` as wall time minus
category-level CUDA-event intervals. CPU submission gaps that occur between
kernels inside a category are already included in those intervals, so a small
`other_idle` value does not prove that launch overhead is negligible. The
existing OPT-096 segment capture scaffold can be reused once actual overhead
is measured.

## Implementation

1. Authenticate one build, model/GGUF, pinned llama revision, CUDA device,
   selectors, compiler flags, clocks/power state, and execution-graph path.
   Record this identity in the report and use it for every A/A and graph run.
2. Run three warmups plus ten interleaved AB/BA pairs of the unchanged Quartz
   control at P4096, D128, and D2048. Report raw latency, tok/s, p50, p95,
   geometric ratios, and confidence intervals. Do not use OPT-098 arrays for
   this interval or reinterpret them as a current control.
3. Capture a representative decode timeline with the least intrusive available
   method (existing scheduler timestamps, CUPTI, or Nsight Systems). Separate
   host launch/submit gaps, GPU idle gaps, kernel intervals, synchronization,
   and graph parameter-update time. The event-category `other_idle` field is
   reported only as a legacy diagnostic, never as the measured launch budget.
4. If removable launch/submit overhead is at least 0.50 ms/token at both D128
   and D2048, run the existing `decode_segments8` capture path against the
   unchanged eager control. Include capture/update cost in token timing and
   verify graph/eager output, state ownership, cancellation, and address
   validity. If either prefix is below the trigger, record `no_graph_opportunity`
   for production and do not add another graph variant.
5. Reconcile the 128K allocation inventory and the OPT-106 `memory_fit` result
   while the build identity is frozen. Explain any byte-level accounting
   discrepancy; do not increase a reserve cap without an allocation-backed
   reason.

## Verification and evidence

- Add a task/iteration contract, fixture, host validator, runner entry, and
  `evidence/optimization/opt114-sitting-and-launch-overhead/REPORT.md`.
- The report must contain an A/A repeatability verdict. A control whose paired
  confidence interval excludes equality or whose point ratio is outside the
  existing 2% measurement guard is `measurement_unstable`; subsequent
  performance tasks must not issue keep/reject claims until a stable sitting
  is obtained.
- For a graph candidate, run 3 warmups plus 10 paired complete-token rounds at
  both prefixes and five uninstrumented engine AB/BA pairs. Report CPU and GPU
  timelines, graph node/update identities, launch counts, p50/p95, and memory.
- Preserve the current numerical, state, and cancellation tests; no quality
  concession is available for a graph path.

## Acceptance and stop rule

- Deliver a reproducible fresh control identity and an honest A/A verdict. A
  historical-vs-fresh discrepancy is recorded as calibration evidence, not
  called an optimization.
- Admit a graph path only when the measured removable overhead reaches
  0.50 ms/token at both D128 and D2048, the paired complete-token saving is
  positive with a 95% interval, and graph/eager/state/memory gates pass.
- If the A/A control is unstable, stop the post-106 performance ladder pending
  a stable environment. If launch overhead is below the trigger or graph A/B
  loses, retain the current eager path and record a measured no-op.

## Non-goals

No new profiling framework, persistent scheduler, prompt graphs, graph sweep,
kernel arithmetic change, benchmark change, historical fixture rewrite, or
production selector change.
