# OPT-108 — Reproduce the actual NVIDIA pinned-llama vector-attention stack

Status: pending. Dependencies: OPT-103, OPT-106, OPT-114. Coupled IDs: none.
Primary target: the matched D2048 attention excess.

## Outcome

Implement one source-faithful llama-style one-query attention vertical slice,
but prove it first on equivalent device buffers before changing the Quartz
engine. The slice may own the query-preparation boundary, partition policy,
and launch organization together. KV representation and math mode are
candidate choices, not assumptions. The current production attention path (or
OPT-107 if it is admitted) remains the control.

## Evidence and rationale

OPT-099's matched family totals are diagnostic and non-additive; they are not a
recoverable 13x attention bound. OPT-103 copied the 128-thread shape but not
the full executed algorithm: Quartz recomputed normalization/RoPE inside each
sequence partition, used a fixed partition count, and used a different tile
softmax/merge schedule. The pinned implementation receives a prepared query,
uses its own 16-byte load and tile-processing organization, chooses partitions
from the actual KV length/occupancy policy, and has translation-unit-specific
math flags. These are the differences to reproduce and measure.

Do not claim that the pinned NVIDIA path uses a half2 V accumulator. In the
pinned source, `V_DOT2_F32_F16_AVAILABLE` is defined only for HIP/AMD targets;
SM120 follows the float2 accumulation branch. Do not make an F16 cache rewrite
an entry requirement: first test the pinned BF16-capable path on the existing
cache, then measure any F16 conversion or cache-lifetime cost separately.

## Implementation

1. Adapt the pinned `flash_attn_ext_vec<256,1>` organization source-faithfully:
   its 128-thread mapping, 16-byte Q/K/V copies, query registers, tile-level
   online max/sum and V sweep, partition/merge behavior, and actual NVIDIA
   accumulation branch. Keep the adapter namespaced and model-specialized.
2. Prepare Q RMSNorm and RoPE once per query head before the partitioned
   traversal. Reuse that prepared query in every partition. Do not repeat the
   normalization, trigonometry, or head reduction per partition.
3. Implement the pinned BF16-KV-compatible path first. An F16 KV candidate is
   allowed only if its conversion is measured outside and inside complete
   attention, its memory cost is recorded, and it is not presented as a free
   speedup. Do not change the long-lived cache solely to satisfy this task.
4. Compute the pinned partition count from actual KV length and the source's
   occupancy policy. Record the effective count; do not hard-code 16 or infer
   an unmeasured count from SM count alone.
5. Preserve the pinned translation-unit math flags only in the candidate TU.
   Test strict math first; test a scoped fast-math build only as a second
   candidate if the source build actually uses it. Record SASS math
   instructions, registers, spills, occupancy, staging bytes, and conversions.
6. Treat the adapter as one coupled candidate. Do not promote an isolated
   faster constituent when complete attention loses. Preserve causal masking,
   Qwen attention scale/gate, candidate-versus-committed visibility,
   transactional commit, full head width/GQA mapping, and public FP32 output.

## Verification and evidence

- Add task/iteration contracts, fixture, source-provenance manifest, native
  correctness and production-shape tests, host validator, runner entry, and
  `evidence/optimization/opt108-llama-vector-stack/REPORT.md`.
- Before engine integration, compare the candidate and control on identical
  query/KV/output buffers at 128, 512, 2048, and 4096 positions. Stop if the
  source-faithful candidate is not faster on that matched primitive; do not
  spend a full engine integration pass on a losing adapter.
- Compare full attention output to an independent FP64 sample oracle at short,
  crossover, D2048, and 4096 positions. Record max/RMS/relative error and all
  nonfinites separately from same-path graph/eager equality.
- Run full candidate NLL/quality, deterministic continuation, checkpoint,
  restore, cancellation, cache round-trip, and 128K memory tests for any
  survivor. Arithmetic changes may not reuse OPT-103 quality evidence.
- Performance acceptance is 3+10 paired complete 16-layer attention rounds and
  five uninstrumented D128/D2048 engine pairs, followed by one P4096 guard.

## Acceptance and stop rule

- Require the matched primitive screen to win before integration, then require
  a positive 95% complete-attention saving of at least 0.50 ms/token at D2048.
  The selected prefix policy must improve D2048 without regressing D128; it may
  fall back to `warp_query` (or OPT-107) below its measured crossover.
- Require no quality regression under the current OPT-091 successor policy,
  no state/cache failure, no nonfinite output, and no loss of the 1.5 GiB 128K
  reserve.
- If the matched primitive or complete candidate fails, retain the current
  production path and stop. Do not split out a cosmetically faster constituent
  after the coupled stack loses.

## Non-goals

No quantized KV, approximate/sparse attention, GQA6 CTA, speculative decoding,
unscoped global fast math, new GGUF, or current llama HEAD as the release
authority. No AMD-only half2 claim or mandatory F16 cache migration.
