# OPT-123 — Measure interactions and admit the combined pipeline stack

Status: pending. Dependencies: OPT-117, OPT-118, OPT-119, OPT-120, OPT-121,
OPT-122. Coupled IDs: none. Priority: P1. Final experimental gate.

## Outcome

Determine whether pipeline changes compose into a faster, quality-admitted
engine. Read [OPT-115](OPT-115.md) and [OPT-116](OPT-116.md). A dependency may
deliver a rejection/no-opportunity verdict; the combined gate must proceed
using the retained path. No optimization is invented inside this gate.

## Freeze and interaction study

1. Freeze post113 as the historical-control identity, one selected combination
   of kept candidates, and pinned llama. Record all source/build, model,
   arithmetic/format/role-map, graph and capacity identities. Rejected paths
   cannot leak into the combination. If none survives, selected equals control
   and is measured once. Reconcile the already-passed OPT-113 memory ledger
   before attributing any new allocation delta.
2. Predeclare a bounded interaction matrix: control, combined, each survivor
   alone on post113 where meaningful, and combined minus each survivor. Reuse
   authenticated parent results where identities match. For a dependent slice,
   test the smallest valid unit rather than an invalid partial configuration.
   Do not run an exhaustive Cartesian selector search.
3. Measure graph × residency and packed-format × consumer interactions explicitly
   when those survivors exist. Explain overlaps: launch savings, bytes saved,
   graph update cost, workspace reuse, lost occupancy and conversions. Do not
   add isolated speedups or claim a winning component survives unchanged in
   combination. Use actual full requests for the matrix.
4. Freeze removal rules before results: if the combination fails a gate, use
   leave-one-out evidence to remove an attributable offending unit, freeze one
   revised combination and run one fresh confirmation. No new variant/tuning
   inside the gate. If still failing, retain the last independently admitted
   valid stack or post113, and publish the unresolved interaction.

## Final verification

- Run all OPT-116 generated-text/NLL/long-state checks on the exact combination
  before long timing. Quality budgets remain anchored to post113 and the
  applicable frozen historical baseline; several individually acceptable
  approximations cannot each consume a new 1% budget. Publish strict and
  successor outcomes separately.
- In a fresh exclusive sitting run post113, selected and pinned llama through
  the shared paired P4096/D128/D2048 protocol, original OPT-113 benchmark
  counts/boundaries, the original OPT-016 2K gate, and the populated long-cache
  workloads frozen in OPT-115. Label these series separately; pair only matched
  runs with identical boundaries. Historical benchmark numbers remain history.
- Run complete sync/sample/eval/output requests with real generation and
  normal cancellation callbacks, reporting TTFT, p50/p95 inter-token latency,
  total request wall, emitted token count and peak memory. Fixed-token engine
  probes remain separately labeled from free-running generation.
- Validate all state, graph/eager, checkpoint and live 128K/reserve checks on
  the combined representation. Include preparation/graph startup cost and
  conversion peaks; do not finance the final stack with an unreported cache.
- Report independent successor-quality internal improvement, pinned-llama
  parity, long-context performance, memory reduction and original OPT-056 +5%
  outcome. The new keep requires paired aggregate throughput lower bound >1
  over P4096/D128/D2048, shared per-workload guards, and all new quality/state/
  memory gates; a long-context-only configuration uses its predeclared target
  and is labeled accordingly. Original OPT-056 still requires its original
  quality, each-workload >=1.05× llama, decode p95 and 2K conditions; successor
  quality cannot silently satisfy the historical strict-quality requirement.
