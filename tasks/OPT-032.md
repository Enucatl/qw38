1. `mixer_mmv` — input projections only

### Next-task order (frozen algorithm)

Record in the fixture as `next_task_order` (array of five IDs) plus the inputs used. Host validation recomputes the array from the live numbers; a mismatch fails. Documentation copies the array; it does not invent a different order.

Definitions:

- `p_gap = llama_p.mean_tok_s / quartz_p.mean_tok_s`
- `d_gap = llama_d2048.mean_tok_s / quartz_d2048.mean_tok_s`
- `decode_deficit_larger` is true iff `d_gap > p_gap` (equality retains attention first)
- D2048 attributed token: `mmv_ms = mixer_mmv + ffn_mmv`, `attn_ms = attention_core`
- `decode_chain = ["OPT-034", "OPT-036"]` if `mmv_ms >= attn_ms`, else `["OPT-036", "OPT-034"]`
- `prefill_chain = ["OPT-033", "OPT-035", "OPT-037"]` always (OPT-035 depends on OPT-033; OPT-037 stays last among prefill because mixer/GDN have no new transferable pending task; FFN tiles remain the trailing prefill idea)

Builder:

1. If `decode_deficit_larger`, append `decode_chain.pop(0)`; else append `prefill_chain.pop(0)` (`OPT-033`).
2. While either chain remains:
   - `trailing_prefill` = count of consecutive prefill IDs at the end of `order`
   - If `decode_deficit_larger`: append the next decode if `decode_chain` is non-empty and (`trailing_prefill >= 2` or `prefill_chain` is empty); else append the next prefill if any remain; else the next decode.
   - Else (retain attention first): append the next decode if `decode_chain` is non-empty and (`trailing_prefill >= 1` or `prefill_chain` is empty); else append the next prefill if any remain; else the next decode.

This reproduces default **033 → 034 → 035 → 036 → 037** when P gap ≥ D2048 gap and `mmv_ms >= attn_ms`. It never schedules three prefills before a remaining decode. It never reorders OPT-035 ahead of OPT-033. It never inserts OPT-031. Mixer MMQ and GDN core have no pending transferable task in this ladder (quality mixer is installed; GDN fusion and PDL stay excluded).

Also record `next_task` as `next_task_order[0]` for readers.

Later OPT-033+ keep/reject uses these published P/D128/D2048 means as the then-current accepted oracles, plus a fresh same-sitting baseline in that later task, plus the cross-workload guard in `speedup-plan.md`. OPT-032 itself does not keep or revert a kernel.
