# OPT-009 — Implement true batched Q8_0/Q4_K/Q6_K prompt MMQ

## Control

- Primary ID: `OPT-009`
- Coupled IDs: `none`
- Dependencies: `OPT-004`, `SCH-002`; both done at planning admission
- Status: `done`
- Ledger acceptance: Prompt projections reuse weight tiles across rows, select measured SM120 kernels, and preserve frozen numeric envelopes

## Goal and boundaries

Replace the production Q8_0 prompt path that launches one GEMV per prompt row
with a weight-reusing Q8_0-by-BF16 MMQ tile, and extend the existing Q4_K/Q6_K
prompt MMQ tiles beyond the OPT-004 maximum of eight prompt rows so a 4,096-row
chunk reuses each decoded weight across a measured SM120 tile. Production
`matrix_prompt` must select those tiles from a checked-in RTX 5090 sweep.
Q8_0 must keep direct BF16 activations (no extra requantization). Frozen CUD-001,
CUD-002, SCH-002, and OPT-008 numeric and exact-state envelopes must still pass.

- Constraints: keep C++17, CUDA 13.0.2, `sm_120`, `--fmad=false`, the pinned
  Qwen3.8-27B Q4_K_M artifact, BF16 activation storage, FP32 accumulation, the
  existing public `Engine`/`Session` API, and all frozen numeric gates. Q8_0
  prompt arithmetic must remain the decode `q8_mmv_bf16` multiply, `__fadd_rn` /
  `__fmul_rn` column walk, and warp shuffle reduction, applied independently to
  each prompt row. Do not route production Q8_0 through `launch_quant_mmq`,
  which requantizes activations to transient Q8 and already failed
  `append_vs_fresh` byte equality during SCH-002. Do not add persistent device
  allocations, change `kPromptChunkRows`, change GDN/attention kernels, or edit
  `Makefile`. Exclusive RTX 5090 work stays serialized. Adapt no llama.cpp,
  DwarfStar, or cuBLAS GEMM implementation.
- Non-goals: tensor-core or cuBLAS GEMM; changing decode Q8_0/Q4_K/Q6_K MMV;
  requantizing Q8_0 activations; changing the 4,096-row outer chunk (`OPT-008`);
  KV layout (`OPT-010`); prompt fusion/overlap (`OPT-011`); prompt graphs
  (`OPT-012`); GDN scan parallelism (`OPT-013`); loosening frozen envelopes;
  claiming end-to-end prefill/decode speedup, comparative 5% gates, or 128K
  quality recovery; editing `plan.md` or `QLT-001`.
- Plan impact: `none`
- Affected interfaces: CUDA-internal MMQ launch and tile-selection APIs in
  `cuda/quant_mmv.h` and the Q8_0 branch of `matrix_prompt`. No public engine,
  CLI, server, checkpoint, model, or JSON API changes. New schema-1 contract
  and fixture files are task evidence, not a public protocol.
- Implementation classification: not mechanical. The work changes CUDA kernel
  occupancy, register tiles, reduction ownership, production projection
  dispatch, and numeric invariants.

## Implementation decisions

Keep decode `q8_mmv_bf16` and Q4_K/Q6_K `launch_quant_mmv` unchanged. Implement
true prompt-row weight reuse in `cuda/quant_mmv.cu` / `cuda/quant_mmv.h`, then
point production `matrix_prompt` at those launchers.

Move the current `q8_mmq_bf16` kernel from `cuda/full_scheduler.cu` into
`cuda/quant_mmv.cu` as a test-only reference named `q8_mmq_bf16_reference`,
exported as `launch_q8_mmq_bf16_reference`. Production must never call it.
Replace it with a templated `q8_mmq_bf16_tiled<PromptTile>` that uses the
CUD-002 ownership model: 256 threads, eight warps, one warp owns one output
row, `blockIdx.y` owns a prompt-row tile rather than a single row. For each
column in the existing lane stride, decode the Q8_0 weight once and apply that
scalar to every in-range prompt row in the tile with the same
`__fmul_rn(weight, __bfloat162float(activation))` and `__fadd_rn` chain used
by `q8_mmv_bf16`. Warp-shuffle-reduce each prompt row independently in the
same 16…1 order, and write token-major `output[prompt_row * output_rows +
output_row]`. Guard partial prompt and output tiles; expose no padding as a
result. Do not stage Q8 activations.

Add CUDA-internal launchers:

- `launch_q8_mmq_bf16(...)` — production; uses
  `selected_mmq_prompt_tile(QuantKind::kQ8_0, prompt_rows)`.
- `launch_q8_mmq_bf16_variant(..., prompt_tile, ...)` — sweep and occupancy.
- `launch_q8_mmq_bf16_reference(...)` — retained row-wise kernel.

Change `matrix_prompt`'s Q8_0 branch to `launch_q8_mmq_bf16`. Leave the Q4_K
and Q6_K branch on `launch_quant_mmq`, which already reuses weights inside a
tile.

Extend `quant_mmq` / `launch_quant_mmq_variant` / `launch_q8_mmq_bf16_variant`
to compile-time tiles `{1,2,4,8,16,32,64}`. Reject any other tile. Keep eight
output rows per block (`(output_rows + 7) / 8` grid X, 256 threads). Do not
add shared memory or tensor-core paths in this increment.

Replace kind-agnostic `selected_mmq_prompt_tile(prompt_rows)` with
`selected_mmq_prompt_tile(QuantKind kind, std::size_t prompt_rows)` and a
one-argument wrapper that calls the Q4_K table so existing CUD-002 assertions
can be updated in one place. `launch_quant_mmq` must pass `kind`. Populate the
tables from a new pinned RTX 5090 sweep, not by copying OPT-004's eight-row
ceiling.

Sweep protocol (same rule as OPT-004, new candidates and shapes):

- Device: exclusive RTX 5090, CUDA 13.0.2, `sm_120`, image `qw38-cuda:13.0.2`.
- Three unrecorded warm-ups, 30 synchronized CUDA-event samples, three
  replicates. Winner is the lowest arithmetic mean across replicates.
- Prompt-row buckets: `1, 2, 4, 8, 16, 32, 64, 256, 4096`.
- Tile candidates: `1, 2, 4, 8, 16, 32, 64`.
- Zero-filled packed weights and activations for timing only.
- Production shapes:
  1. Q8_0-BF16 `12288 × 5120` (attention Q/gate).
  2. Q4_K `17408 × 5120` (FFN gate/up).
  3. Q4_K `5120 × 17408` (FFN down).
  4. Q6_K `5120 × 6144` (attention output).
- Q8_0 winners come from shape 1. Q4_K winners minimize the sum of means of
  shapes 2 and 3. Q6_K winners come from shape 4.
- A candidate that fails to launch, produces a non-zero synthetic output, or
  reports `cudaOccupancyMaxActiveBlocksPerMultiprocessor == 0` cannot win and
  remains in the raw loser set.
- Write every sample to
  `evidence/profiling/opt009-mmq-tile-sweep-raw.txt` and every replicate mean
  plus the selected buckets into `fixtures/cuda_prompt_mmq.json`.
- Do not mutate `fixtures/cuda_dispatch_tuning.json` or
  `pins/cuda_dispatch_tuning_contract.json`. OPT-004 remains the MMV-bucket
  and historical ≤64-row Q4_K MMQ authority. OPT-009 supersedes production
  MMQ prompt-tile selection.

After the sweep, hard-code the winning `kind × maximum_prompt_rows → tile`
conditionals in `selected_mmq_prompt_tile`. Update
`cuda/quant_mmv_test.cu` dispatch assertions to those values. Small CUD-002
cases (1/3/5/9 prompt rows) continue to use tiles 1/4/8 as selected by the
new table and must still pass the frozen `5e-4` / `2.5e-4` envelopes.

Add a dedicated native diagnostic `cuda/prompt_mmq_test.cu`, built with the
same explicit pinned `nvcc` command OPT-007 used (do not add a Makefile
target), printing one `QW38_PROMPT_MMQ_RESULT=` JSON record. Python
`tests/test_cuda_prompt_mmq.py` validates that record against
`pins/cuda_prompt_mmq_contract.json` and the regenerated fixture. The
diagnostic must:

1. Compare production `launch_q8_mmq_bf16` to `launch_q8_mmq_bf16_reference`
   on nonzero packed Q8_0 fixtures at prompt rows `1, 3, 5, 8, 9, 64, 65`
   and output sizes `17` and `1024` / columns `256` and `5120`. Require
   byte-identical token-major outputs (same per-row FMAs and shuffle order).
2. Compare `launch_quant_mmq` tiles `{1,8,selected}` for Q4_K and Q6_K on
   the existing CUD-002 shapes plus a `64 × 257 × 512` case; require
   byte-identical outputs across tiles and the frozen CUD-002 absolute/RMS/
   exact-Q8-staging/nonfinite envelopes versus the scalar decoder.
3. Capture each production launcher into a CUDA graph at 64 and 4096 prompt
   rows and require `grid.y == ceil(prompt_rows / selected_tile)` and
   `grid.x == ceil(output_rows / 8)`, versus the reference Q8_0 graph where
   `grid.y == prompt_rows`. One kernel node per launch remains required.
4. Report selected-kernel occupancy `>= 1` active block per SM, registers
   `> 0`, and compiler-reported local bytes per thread `<= 1024`.
5. Time Q8_0-BF16 64-row and 256-row `12288 × 5120` production versus the
   row-wise reference (3 warm-ups, 30 samples). Require the production mean
   to be strictly below the reference mean. Time Q4_K `17408 × 5120` at
   4096 rows for tile 8 versus the selected tile; require selected mean
   `<=` tile-8 mean. These are component predicates, not end-to-end claims.
6. Reject null pointers, zero rows, non-multiples of 256 columns, and illegal
   tiles with `cudaErrorInvalidValue`.

Do not change scheduler workspace sizes. `prompt_q8_` remains Q4_K/Q6_K
scratch. Q8_0-BF16 uses no extra workspace. Inherited prompt-scheduler
4,097-row exact state/hidden/logits comparison, cancellation, and memory-fit
reserve gates are regressions, not new fixtures.

Documentation updates belong to the documentation stage: explain weight-tile
reuse versus the old Y=`prompt_rows` grid, the BF16-versus-Q8-staged split,
the new tile buckets, the retained reference kernel, measurement protocol,
and the component-only proof limit. Add an OPT-009 audit row with a
non-final marker while the ledger status is `in_progress`.

- Invariants: Q8_0 prompt results stay byte-identical to the retained
  row-wise BF16 kernel; Q4_K/Q6_K stay within the frozen CUD-002 envelopes
  and bit-identical across legal tiles; decode MMV, GDN, attention, chunk
  policy, atomic commit, cancellation, checkpoints, and 128K reserve are
  unchanged; production tile selection is a pure function of `kind` and

- Rejected alternatives: routing production Q8_0 through `launch_quant_mmq`

  (unmeasured architecture change; occupancy-failed large register tiles
