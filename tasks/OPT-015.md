### Why llama.cpp reaches thousands of tok/s at 2K

The report must explain these pinned-revision mechanisms, with file-level citations to the `cc83d7b` checkout (or the equivalent GitHub blob URLs at that revision):

1. **Quantized MMQ is MMA/tensor-core, not scalar FMA.** Ampere/Blackwell Q4_K MMQ tiles are 256 threads × 128 output rows × J prompt columns up to 128, with Q8_1 shared-memory staging (`mmq.cuh`, `mmq-config-ampere.cuh`). Quartz FFN at 2048 uses tile 4 and `__fmul_rn`/`__fadd_rn`. This is the dominant reason llama.cpp is thousands of tok/s: FFN/MMQ is 77% of Quartz 2K wall, so even zero GDN and attention would leave Quartz at `2048 / 32.295 ≈ 63` tok/s.
2. **Microbatch 512 still has enough rows for those MMA tiles.** `n_ubatch=512` is smaller than Quartz's 2048-row chunk, so llama.cpp is not faster because it batches more prompt rows. Quartz already has more rows than llama.cpp's ubatch and still loses on arithmetic intensity per weight byte.
3. **Fused GDN kernel walks the ubatch in one launch per head.** `gated_delta_net.cu` holds `S` in registers and loops `t = 0 .. n_tokens`. Quartz still pays windowed launches plus the OPT-013 intra/prefix/from-state trio. GDN is 12.6% of Quartz 2K, so this is the second sink, not the first.
4. **Flash attention auto (MMA F16).** `llama-bench` `flash_attn: -1` selects `fattn-mma-f16`. Quartz attention is tiled causal GQA (OPT-005–OPT-007) without MMA. Attention is 10.4% of Quartz 2K.
5. **CUDA graphs in ggml** amortize launch overhead on the ggml graph. Quartz 2K `graph` is measured 0 ms. Graphs are not the present gap.

llama.cpp's Qwen3.5 graph (`src/models/qwen35.cpp`) is the same hybrid 48 GDN + 16 attention contract. The speed gap is kernel/dispatch quality on the same GGUF, not a different model policy.
