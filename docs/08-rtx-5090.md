# 8. RTX 5090 profiling and optimization

[Previous](07-engineering-method.md) · [Index](README.md) · [Next](09-engine-comparison.md)

## Why this matters

The target is a specific 32 GiB Blackwell card. Optimization follows measured
wall-time attribution; architecture marketing numbers do not identify the next
bottleneck.

Profiling is a measurement loop: first establish a correct baseline, then find
where its elapsed time actually goes, change one cause, and rerun the same
fixture. A **kernel** is a GPU function launch; a **launch gap** is time when the
GPU is idle while the CPU schedules the next launch. A kernel can have high
occupancy and still be slow if it moves too many bytes or waits on dependencies.

## Reproducible baseline

Record GPU model/VBIOS, driver, CUDA toolkit, compiler flags and `sm_120` versus
architecture-specific targets, clocks/power/temperature, model and converter
hashes, quant policy, context, prompt/output, batch, graph state, and raw timing
samples. Warm up deliberately and alternate A/B order.

These controls matter because GPU frequency changes with temperature and power,
the first run may compile or populate caches, and a driver/toolkit change can
select different machine instructions. Alternating A/B order means running
`A,B,A,B...` rather than all baseline runs followed by all candidate runs; it
reduces the chance that warming or throttling is incorrectly credited to one
variant.

Use Nsight Systems first: locate CPU gaps, copies, synchronization, graph launch
islands, and per-phase wall time. Use Nsight Compute only on attributed kernels:
DRAM throughput, Tensor Core utilization, instructions, registers, spills,
shared memory, achieved occupancy, and warp stalls. Occupancy is a constraint,
not the objective.

Nsight Systems answers “when was the CPU or GPU busy?” It is the timeline view.
Nsight Compute answers “what happened inside this selected kernel?” Common
counters need interpretation:

- **DRAM throughput:** rate of traffic to device memory; near a measured ceiling
  suggests bandwidth pressure, but low throughput can also mean poor access.
- **Tensor Core utilization:** how much supported matrix hardware was active;
  irrelevant for kernels intentionally using scalar/vector instructions.
- **Registers and spills:** per-thread fast storage and values forced into slower
  local memory when registers run out.
- **Occupancy:** how many warps can reside relative to the hardware maximum;
  enough warps can hide latency, but maximizing the percentage can reduce reuse.
- **Warp stalls:** sampled reasons a group of threads could not issue work, such
  as waiting for memory, dependencies, or synchronization.

## Optimization sequence

1. Establish scalar and high-precision CUDA correctness.
2. Log complete allocations and demonstrate 32 GiB headroom.
3. Split MMV decode from MMQ prefill and eliminate accidental transfers.
4. Attribute GDN, attention, FFN, logits, sampling, and launch gaps.
5. Tune the largest measured kernel with boundary fixtures at every change.
6. Fuse only attributed intermediate traffic/launches.
7. Capture stable decode and fixed-shape batch paths.
8. Change scheduling or batching only after reporting queueing effects.

At each step retain the previous implementation as a comparison point until the
new path passes correctness and shows a repeatable wall-time improvement. A
kernel that is 20% faster but accounts for 2% of decode can improve the request
by at most about 0.4% before secondary effects; this simple attribution prevents
spending weeks on an impressive but irrelevant microbenchmark.

FP4 storage and FP4 Tensor Core arithmetic are separate. A format needs matching
block scales, activation conversion, supported MMA/layout/toolchain, and enough
rows to amortize setup. Decode can remain byte/launch-bound. Treat all expected
5090 behavior as **Proposed** until this protocol measures it.

FP4 illustrates the difference between representation and execution. A file can
store four-bit codes even if the GPU kernel expands them to FP16 and uses FP16
math. Native FP4 matrix instructions require the exact supported value format,
scale layout, activation conversion, matrix orientation, and architecture target.
Even then, conversion overhead can outweigh the faster arithmetic at `T=1`.

## Worked experiments

Sweep prompts 1, 128, 2K, 8K and outputs 256; batch 1/2/4/8; context 0, 32K,
and the maximum admitted by the allocation ledger. Report TTFT, ITL distribution,
prompt/aggregate throughput, peak memory, and correctness. For each optimization
publish baseline/candidate medians plus raw samples and profiler attribution.

The median is the middle observation and resists one unusually slow run; p95 is
the value below which 95% of observations fall and exposes tail latency. Keep
raw samples because a single summary cannot reveal bimodal behavior, thermal
drift, or periodic checkpoint costs.

q27 demonstrates externally that a narrow Qwen engine can exploit specialization
on a 5090, but its artifact, kernels, benchmark harness, and results are its own.
It is neither a DwarfStar result nor an acceptance threshold for this engine.

## DwarfStar transfer boundary, failures, and exercise

Reuse its benchmark discipline, graph allocation accounting, and CPU/GPU gates.
Adapt shapes and target-specific kernels. Reject cross-model performance
extrapolation. Common failures are tuning profiler counters rather than wall
time, hiding cold starts, omitting failed/OOM samples, and comparing different
quality or reuse.

Exercise: profile 1-token decode and 256-token prefill. Expected: an attributed
bottleneck list with percentages, not a preconceived answer; the next change
targets the largest actionable component and preserves the correctness fixture.
