A Chat Completions request is not a model prompt. It is a JSON description of
messages and generation controls. Quartz validates that description, renders the
exact Qwen template, tokenizes it, runs the model, and translates generated
tokens into one JSON response or a stream of events.

## JSON from first principles

**JSON** has six value kinds: object, array, string, number, boolean, and `null`.
An object maps quoted names to values; an array is an ordered list:

```json
{
  "model": "qwen3.8-27b-q4_k_m",
  "messages": [{"role": "user", "content": "Say hello"}],
  "temperature": 0
}
```

Strings use escapes: `\n` represents a newline and `\u00e9` a Unicode code
point. Characters beyond the Basic Multilingual Plane use a high/low
**surrogate pair**; `\uD83D\uDE02` is 😂. Quartz combines the pair into the
corresponding four UTF-8 bytes.

[`server_json.cpp`](../src/server_json.cpp) is a narrow recursive-descent parser:
each function consumes one grammar production—a value, object, array, string, or
number—from left to right. It rejects duplicate object names, malformed numbers
and escapes, invalid UTF-8, unmatched surrogates, trailing bytes, and nesting
beyond 64 levels. HTTP bodies are capped at 1,048,576 bytes. These limits prevent
small malicious inputs from demanding unbounded stack or memory.

Objects are stored with sorted names. **Canonical serialization** writes that
stable order, so semantically identical tool definitions produce identical Qwen
prompt bytes. The spaced form matches the frozen official template fixture;
ordinary responses use compact JSON.

## The HTTP boundary

Generation uses:

```text
POST /v1/chat/completions HTTP/1.1
Content-Type: application/json
Content-Length: ...
```

`POST` carries the request body. `Content-Length` gives its exact byte count.
Quartz rejects a missing or invalid length, an early end, an oversized body, and
chunked transfer encoding. The content type must begin with `application/json`.
The TCP connection still closes after one request.

Unknown fields and unsupported values fail explicitly. Silently ignoring
`response_format`, for example, could make a client believe structured output
was enforced when it was not.

## Accepted fields

| Field | Quartz v1 behavior |
|---|---|
| `model` | Exactly `qwen3.8-27b-q4_k_m` |
| `messages` | System/developer/user/assistant/tool history |
| `max_tokens` / `max_completion_tokens` | One limit from 1 through 8,192 |
| `temperature` | 0 through 2; zero selects greedy decoding |
| `top_p` | Greater than 0 and at most 1 |
| `top_k` | Quartz extension, 0 through vocabulary size |
| `seed` | Unsigned deterministic sampler seed |
| `stop` | One string or up to four strings |
| `reasoning_effort` | `none`, `low`, `medium`, `high`, or `xhigh` |
| `chat_template_kwargs.enable_thinking` | Explicit thinking switch |
| `tools`, `tool_choice` | Function tools; auto/none/required/named choice |
| `stream` | One JSON response or server-sent events |
| `stream_options.include_usage` | Final usage-only stream event |

Only `n=1`, false `parallel_tool_calls`, false `logprobs`, zero presence and
frequency penalties, and false `store` are accepted. Image, audio, file,
structured-output, legacy-function, metadata, and unknown controls are rejected.
This describes measured Quartz behavior, not the complete OpenAI API.

## Roles, content, and reasoning

- `system` and leading `developer` messages establish instructions.
- `user` contains a query.
- `assistant` can contain prior content, reasoning, and function calls.
- `tool` contains a result and names its earlier call ID.

Content may be a string or an array of text/input-text parts. Non-text parts fail
before tokenization. System/developer records must stay at the beginning, and at
least one user query must exist.

The parser produces public `ChatMessage` values. The engine invokes the already
admitted official Qwen template described in [Chapter 16](16-chat-template.md).
The HTTP layer never reads tensors, GDN state, KV rows, or CUDA pointers.

Reasoning `high` maps to the pinned Qwen `xhigh` instruction. `none` renders a
closed empty `<think>...</think>` prefix, making all generated bytes answer
content. With thinking enabled, bytes before the generated `</think>` become
`reasoning_content`; bytes after it become `content`.

## Function calls and results

A function tool has a name, optional description, and JSON Schema parameters.
Quartz canonicalizes the definition before the template places it in Qwen's
`<tools>` block.

Historical assistant arguments may be a JSON object or a string containing one.
The template converts them to Qwen `<parameter=name>` elements. Consecutive tool
results become the exact grouped tool-response block required by the template.

The model emits Qwen XML. Quartz recognizes complete `<tool_call>` and
`<function=name>` blocks, requires a declared function, and returns OpenAI-style
`tool_calls`. JSON Schema decides whether each returned parameter is a string,
number, integer, boolean, object, array, or null. A value that violates its
declared type is not presented as a valid call.

`tool_choice: "none"` removes definitions from the prompt; `auto` allows a call
or normal answer. `required` adds a developer instruction requiring a declared
function; a named choice requires that function. If the model violates a
required/named choice, Quartz fails the request rather than relabeling prose as a
call. Multiple sequential calls are supported; parallel calls are not.

## Single-session generation

After validation, a disconnect monitor starts and the request enters the FIFO
gate. Headers expose arrival depth and measured wait time as
`X-QW38-Queue-Depth` and `X-QW38-Queue-Us`. Only the active ticket can touch the
one GPU session.

1. Render and tokenize the full history.
2. Reject prompt plus requested output beyond 131,072 tokens.
3. `Session::sync` reuses an exact prefix or resets and replays divergence.
4. `Session::sample` chooses a token without committing sampler state.
5. `Session::eval` atomically commits that token and sampler state.
6. Decode output and check the end token, custom stops, and token limit.

End token and custom stop produce `finish_reason: "stop"`; token exhaustion
produces `"length"`; a valid call produces `"tool_calls"`. Usage contains prompt,
completion, and total token counts. A stop string is omitted from visible output.
Quartz withholds a suffix that might begin a longer stop, so a stop split across
tokens cannot leak its first bytes.

## Streaming and SSE

With `"stream": true`, the response type is `text/event-stream`. **Server-sent
events (SSE)** are UTF-8 records separated by a blank line:

```text
data: {"object":"chat.completion.chunk",...}

data: [DONE]

```

The first chunk declares the assistant role. Later `delta` objects carry new
`reasoning_content` or `content`. The final choice carries the finish reason;
optional usage is a separate event with an empty choices array; `[DONE]` ends the
stream.

Tokens are not necessarily character boundaries. A token may end midway through
a multi-byte UTF-8 character. Quartz emits only the largest complete prefix and
holds the rest for the next token. It likewise withholds a partial `</think>` or
custom stop. Tool XML is held until a complete validated call exists, preventing
internal XML from leaking as assistant prose.

## Cancellation and atomic state

A monitor polls the TCP socket while the request waits and runs. Peer disconnect
or server shutdown sets one atomic flag. The FIFO gate removes a cancelled
waiter. Prompt replay and each token evaluation pass the flag into CUDA
`EvalControl`, which polls between layers.

Cancellation within a token leaves its candidate GDN/KV/output state unpublished
(the SES-002 guarantee). Earlier complete response tokens may remain committed;
the next exact `sync` reuses its own prefix or resets and replays, preventing
cross-request contamination. `/health` exposes a monotonic
`cancelled_requests` counter for diagnosis.

## Run it

Start the CUDA server as in [Chapter 58](58-http-server-core.md), then:

```bash
curl http://127.0.0.1:8080/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"qwen3.8-27b-q4_k_m","messages":[{"role":"user","content":"Reply with exactly: hello"}],"reasoning_effort":"none","temperature":0}'
```

Add `"stream":true` and use `curl -N` to observe SSE chunks.

## Evidence and proof boundary

**Measured, native:** strict/canonical JSON, Unicode surrogates, duplicate keys,
depth limits, roles, text parts, tools/history/choice, sampling, streaming,
explicit exclusions, reasoning/tool output, stop withholding, and partial UTF-8
pass the focused diagnostic.

**Measured, RTX 5090:** the live server produced exact non-streaming and streamed
greedy replies, processed a canonical tool prompt and custom stop, admitted a
second request at queue depth one, cancelled an already-active request after its
client disconnected, remained healthy, and exited cleanly. Measurements are in
[`chat_completions.json`](../fixtures/chat_completions.json).

**Proof boundary:** SRV-002 proves text Chat Completions for one GPU session. It
does not prove Responses, `previous_response_id`, authentication, TLS, persistent
connections, remote deployment safety, continuous batching, concurrent GPU
sessions, structured output, multimodal input, quality, or comparative speed.
